WinASM65 pour VS Code

Ce document explique comment l'extension construit un projet 6502, lance Mesen2 et permet de déboguer au niveau des lignes de source. Il couvre chaque couche, du script Lua dans l'émulateur jusqu'au TypeScript de l'extension.

Vue d'ensemble

L'extension écrite en TypeScript ne fait presque rien elle-même. Elle lance WinASM65.Tooling.exe, un programme .NET qui fonctionne en trois modes. Chacun réutilise l'assembleur et le noyau du moniteur, sans les dupliquer.

Les flèches indiquent qui appelle qui. Monitor.Core s'appuie lui-même sur l'assembleur WinASM65.

Un seul binaire

Les trois modes sont dans un même exécutable autonome (fichier unique, sans .NET installé), livré dans le bin/ de l'extension avec les scripts Lua.

Aucune logique dupliquée

Le build, les listings et le protocole du bridge sont les mêmes que dans le moniteur terminal. Une correction profite aux deux interfaces.

stdout réservé au protocole

En modes --dap et --lsp, stdout sert de canal protocolaire. Console.Out est redirigé vers stderr dès le démarrage.

Pas de bibliothèque protocolaire

DAP et LSP utilisent le même encadrement Content-Length. Le tout est écrit à la main sur System.Text.Json, sans nouveau paquet NuGet.

Le bridge Mesen2

bridge_mesen2.lua tourne dans Mesen2. Il écoute un seul client TCP sur 127.0.0.1. Le port est lu dans la variable d'environnement MACHINE_PORT (45678 par défaut). Le lanceur ouvre d'abord trois réglages dans le settings.json de Mesen2 : AllowIoOsAccess, AllowNetworkAccess et ScriptTimeout.

Protocole

Le protocole est en texte ASCII, une ligne par message. Chaque commande reçoit exactement une réponse, OK … ou ERR raison, dans l'ordre. Les lignes qui commencent par PUSH ne sont pas des réponses : ce sont des messages que le bridge envoie de lui-même.

CommandeRéponse
PINGOK Mesen2 2.1.1. Le nom et la version déterminent les capacités annoncées.
READ $addr n · WRITE $addr hexMémoire, 4096 octets au plus par commande. Une écriture est relue pour vérification ; une écriture en ROM est refusée.
CPUOK pc=$C01A a=90 x=00 y=5E sp=F8 ps=85 cycles=…
PAUSE · RESUME · STEP · RESETContrôle de l'exécution.
BREAK SET|REMOVE exec $addr · BREAK CLEAR · BREAK LISTPoints d'arrêt (et points de surveillance read/write, qui ne font que journaliser).
STATUSOK running ou OK stopped reason=… pc=$… prg=…. Sert à se resynchroniser si un PUSH a été perdu.
STATE SAVE · STATE LOAD hex · ROMSauvegardes d'état et informations sur la cartouche.
Message spontanéQuand
PUSH RAM $0010:42 $0011:43 …Les octets écrits par le programme, regroupés par trame.
PUSH STOPPED reason=breakpoint|step|pause pc=$C01A prg=$0001ALa machine vient de s'arrêter. prg est l'offset du PC dans la PRG-ROM (emu.convertAddress), ou - s'il est inconnu.
PUSH RESUMEDLa machine repart, après RESUME ou RESET. Un STEP n'envoie pas de RESUMED : il est suivi directement d'un STOPPED.

Deux façons de servir les commandes

  • Machine en marche. on_tick s'exécute à chaque lecture de la manette (inputPolled), soit environ une fois par trame. Il arrête l'exécution, traite jusqu'à 64 commandes en attente, envoie le PUSH RAM, puis relance.
  • Machine arrêtée. L'événement codeBreak appelle serve_blocked. Celui-ci annonce PUSH STOPPED, puis traite les commandes dans une boucle bloquante jusqu'à RESUME, STEP ou RESET. Il envoie PUSH RESUMED en sortant, sauf après un pas.

S'arrêter avant l'instruction. Le callback d'exécution de Mesen2 se déclenche au chargement de l'opcode. Un emu.breakExecution() à cet instant arrête la machine après l'instruction. Le bridge demande donc à la place un pas d'un seul cycle CPU (emu.step(1, cpuCycleStep)). La machine s'arrête juste après le chargement de l'opcode, alors que les registres et la mémoire n'ont pas encore changé. Le STEP ou RESUME suivant exécute l'instruction une seule fois. Ce comportement a été mesuré sur Mesen2 2.1.1.

Points d'arrêt muets pendant un reset. reset_now relance la machine avant d'appeler emu.reset(). Le programme exécute donc encore quelques instructions entre les deux. Un point d'arrêt touché à ce moment-là arrêterait la machine juste après le reset, sur le vecteur de reset, avec la mauvaise raison. Les callbacks sont donc ignorés jusqu'à l'événement reset de l'émulateur.

Le client .NET du bridge

ProtocolClient

Un thread récepteur lit les lignes qui arrivent. Les lignes PUSH déclenchent l'événement PushReceived, les autres vont dans une file de réponses. Send() est sérialisé par un verrou : les réponses n'ont pas d'identifiant, donc deux threads qui enverraient en même temps (le polling RAM et la session) risqueraient de prendre chacun la réponse de l'autre.

BridgeMemoryBackend

Il implémente IMemoryBackend ainsi que plusieurs capacités optionnelles :

  • ICpuStateSource : les registres, via CPU.
  • IExecutionEvents : les événements Stopped/Resumed, IsStopped et LastStop, alimentés par les PUSH et par STATUS à la connexion. Si le bridge répond ERR à STATUS (MesenCE), ReportsExecutionState vaut false.
  • IBreakpointRemoval : BREAK REMOVE d'un point d'arrêt unique.
  • IReconnectable, IRomTransferTarget, IExecutionAdapter.

Le polling RAM de secours lit $0000–$07FF toutes les 250 ms et le compare à une copie prise avant la lecture. Il est désactivé quand la machine est arrêtée. L'adaptateur DAP le coupe complètement avec poll: false, puisqu'il ne lit la mémoire qu'à la demande.

Règle du thread récepteur. Stopped et Resumed sont déclenchés sur le thread récepteur. Or c'est ce même thread qui livre les réponses : un gestionnaire qui enverrait une commande depuis ce thread attendrait sa réponse indéfiniment. Les gestionnaires doivent donc seulement mettre le travail en file. C'est ce que fait l'adaptateur DAP.

La carte source

Pour relier un PC à une ligne de source, il faut les adresses que le build a réellement produites, et non celles d'un fichier assemblé isolément. Les adresses d'une unité dépendent en effet de l'adresse de chargement de la cible, de la carte mémoire et de l'ordre des unités dans le projet.

Ce que le build capture

Avec ProjectBuildOptions.CaptureListing, chaque unité reçoit un InMemoryListingService. Le résultat contient alors :

  • ProjectUnitResult.Listing : les lignes de listing (numéro de ligne, fichier source avec les inclusions, adresse, octets).
  • ProjectUnitResult.Origins : chaque .org sous forme de paire (offset dans le .o, adresse). Un .o contient les octets émis bout à bout, sans remplissage entre les .org.
  • ProjectBuildResult.Placements : l'offset de chaque fichier de Output.Files dans l'image, calculé avec la même règle que BinaryCombiner (dans l'ordre, chaque fichier complété jusqu'à sa Size).

Calcul de l'offset PRG

offset dans le .o   = début de l'origine + (adresse − adresse de l'origine)
offset dans l'image = placement du .o + offset dans le .o
offset PRG          = offset dans l'image − 16 (en-tête iNES, + 512 si trainer)

SourceMap

  • AtLine(fichier, ligne) : toutes les émissions d'une ligne (une macro ou un .rep peuvent en produire plusieurs).
  • AtAddress(pc) : toutes les lignes assemblées à une adresse CPU. Il y en a plusieurs quand des banques partagent l'adresse.
  • Resolve(pc, prg) : la réponse est exacte si l'offset PRG est connu ; sinon le premier candidat est renvoyé, marqué « ambigu ».
  • TryNearestEmittingLine : un point d'arrêt sur un label ou un commentaire est déplacé sur la première ligne qui émet du code, dans les 5 lignes suivantes.
  • NearestLabel et Symbols : nomment la frame (NMI+2) et servent à l'évaluation dans la console.

Un test le vérifie sur l'exemple Bomberman : pour chaque ligne cartographiée, l'image construite contient bien l'opcode de cette ligne à l'offset PRG calculé.

Unités sans .org. L'assembleur place leurs premiers octets à son origine par défaut, c'est-à-dire l'adresse de chargement de la cible. Le listing en mémoire part donc de cette adresse (InMemoryListingService.StartAddress, réglée par ApplyDefaultOrigin) et non de 0. ProjectSession.ListSourceText applique aussi la cible du projet (CPU, adresse de chargement, symboles matériels), comme le fait Build.

Le débogueur (DAP)

DebugSession traite les requêtes VS Code et les événements de la machine sur un seul thread, à travers une BlockingCollection<Action>. Le build, le lancement et la connexion passent par IDebugEnvironment, que les tests remplacent par une machine factice.

Séquence de lancement

Avec stopOnEntry, l'adaptateur pose avant le RESET un point d'arrêt temporaire sur le vecteur de reset ($FFFC). L'arrêt est alors rapporté avec la raison « entry ».

Interprétation d'un arrêt

  1. Avant configurationDone, l'arrêt est seulement mémorisé (c'est la pause du lancement).
  2. Si l'arrêt tombe sur un point d'arrêt temporaire et sur aucun point d'arrêt de l'utilisateur, la raison rapportée est « step » ou « entry », et les temporaires sont retirés.
  3. Si l'adresse porte un point d'arrêt de l'utilisateur mais que l'offset PRG désigne une autre banque, l'adaptateur relance la machine sans rien dire à VS Code.
  4. Sinon, la raison est « breakpoint » (avec hitBreakpointIds), « step » ou « pause ».

Un PUSH RESUMED que l'adaptateur n'a pas provoqué lui-même (par exemple un clic dans la fenêtre de Mesen2) devient un événement continued. Un minuteur détecte la perte de connexion et la sortie de l'émulateur, puis envoie terminated.

Le serveur de langage

LanguageServer fonctionne en synchronisation complète : le client envoie le texte entier du fichier à chaque modification. Toutes les requêtes sont traitées sur un thread de travail. Il s'appuie sur deux sources, chacune utilisée là où elle est exacte :

À l'ouverture et à l'enregistrement exact

Build complet du projet qui gouverne le fichier, avec les fichiers .symb dans un dossier temporaire. Les diagnostics sont publiés sur chaque fichier cité, inclusions comprises. Les fichiers corrigés reçoivent une liste vide.

Pendant la frappe 250 ms

Le texte non enregistré est assemblé par ProjectSession.ListSourceText avec les symboles du dernier build réussi. Tant qu'aucun build n'a réussi, les « Undefined symbol » sont retenus, car le nom peut être défini dans une autre unité.

  • Projet gouvernant. C'est le config.json qui déclare le fichier comme entrée (ProjectConfigLocator). À défaut, c'est le plus proche au-dessus : le fichier est alors traité comme une inclusion, et seul le build parle de lui. S'il n'y en a aucun, le fichier est assemblé seul.
  • Survol. Sur une mnémonique : ses formes, avec mode, opcode et taille issus de InstructionDocs. Sur un symbole : sa valeur. Sur une ligne : l'adresse et les octets assemblés.
  • URI. VS Code encode les deux-points du lecteur (file:///c%3A/…). Le serveur les décode, et republie avec l'URI exacte reçue pour les fichiers ouverts.

L'extension VS Code

src/extension.ts enregistre quatre éléments :

  • Résolution de l'outil. Dans l'ordre : le réglage winasm65.toolingPath, puis bin/WinASM65.Tooling.exe dans l'extension, puis le build Debug du dépôt (../WinASM65.Tooling/bin/Debug/net8.0/WinASM65.Tooling.dll, lancé par dotnet).
  • DebugAdapterDescriptorFactory. Démarre l'outil avec --dap.
  • DebugConfigurationProvider. Avec F5 sans launch.json, il prend le config.json le plus proche du fichier ouvert (sinon le premier du workspace). Il ajoute winasm65.emulatorPath si la configuration n'en donne pas.
  • TaskProvider. Une tâche « build <config.json> » par projet, qui lance --build avec le problem matcher $winasm65 (^(.+?)(?::(\d+))?: (error|warning): (.*)$).
  • LanguageClient. Démarre l'outil avec --lsp, pour le langage winasm65 (.nas, .asm). Le réglage winasm65.languageServer.enabled le désactive.

Dans package.json, l'extension déclare aussi la grammaire TextMate syntaxes/winasm65.tmLanguage.json, la configuration de langage (commentaires ;) et l'autorisation de poser des points d'arrêt dans les fichiers winasm65.

Colonne de listing

Le menu contextuel de l'éditeur propose Show Listing / Hide Listing pour les fichiers winasm65. Ces commandes basculent une colonne grise, à gauche du source, avec l'adresse et les octets de chaque ligne, comme dans un fichier .lst :

C000 78        SEI
C001 A9 00     LDA #0
C003 8D 01 20  STA PPU_CTRL_REG2
               NMI:
C01A 48        PHA
  • Données. Requête LSP personnalisée winasm65/listing { textDocument.uri }, qui renvoie rows: [{ line, address, bytes, more }]. Une unité est listée à partir de son texte non enregistré, avec les symboles du projet. Un fichier inclus n'existe que dans une unité : ses lignes viennent donc du dernier build réussi (CaptureListing). more signale qu'une ligne a produit plusieurs émissions (macro, .rep).
  • Affichage. src/listing.ts pose une décoration before sur chaque ligne : vide (espaces insécables) pour les lignes sans code, afin de garder l'alignement. Au plus 3 octets sont affichés, suivis de … s'il y en a d'autres.
  • Mise à jour. Au changement d'éditeur visible, 300 ms après une frappe, et 500 ms après un enregistrement (le serveur reconstruit alors le projet). L'état affiché ou masqué est mémorisé par workspace, et le contexte winasm65.listingVisible choisit l'entrée de menu.

Panneau RAM

Le panneau RAM montre les 2 Ko de RAM de la NES ($0000-$07FF) en hexadécimal et en ASCII. Il s'ouvre au premier arrêt d'une session (réglage winasm65.ram.openOnStop), avec la commande WinASM65: Show RAM, ou avec le bouton de la barre de débogage.

  • Lecture. Requête DAP standard readMemory { memoryReference: "0x0000", count: 2048 }, envoyée par session.customRequest. SP est obtenu par evaluate SP. Les noms viennent une fois par session de la requête personnalisée winasm65.symbols { from, to }, qui renvoie les symboles du build dont la valeur tombe dans la plage.
  • Déclencheurs. Un DebugAdapterTracker écoute les messages de l'adaptateur : stopped provoque un rafraîchissement, continued affiche « running ». La case Live relit la RAM toutes les 500 ms pendant que la machine tourne.
  • Affichage. La page zéro et la pile sont teintées, l'octet en $0100+SP est encadré, et les octets modifiés depuis l'arrêt précédent sont surlignés. L'infobulle donne l'adresse, les noms et la valeur. Une variable déclarée comme NAME = $0B est une constante comme les autres : une petite constante peut donc partager une adresse avec une variable, et tous les noms sont affichés.
  • Édition. Un double-clic sur un octet ouvre une saisie hexadécimale. Entrée envoie writeMemory ; un refus du bridge (écriture en ROM) s'affiche dans la barre d'état du panneau.

Build et paquet

cd vscode-extension
npm install
npm run package
#  1. dotnet publish WinASM65.Tooling -r win-x64 --self-contained -p:PublishSingleFile=true -o bin
#     (bin/WinASM65.Tooling.exe + bin/Bridge/*.lua)
#  2. copie de LICENSE.txt (zlib)
#  3. vsce package --target win32-x64  →  winasm65-win32-x64-0.2.4.vsix (≈ 30 Mo)
code --install-extension winasm65-win32-x64-0.2.4.vsix

Pour développer sans paquet, ouvrez vscode-extension/ dans VS Code et appuyez sur F5. La configuration « Run the extension » compile le TypeScript et WinASM65.Tooling, puis ouvre l'exemple Bomberman dans une fenêtre de développement.

La publication est sérialisée (-maxcpucount:1) : WinASM65 est référencé à la fois par Tooling et par Monitor.Core, et deux compilations parallèles se disputaient la même DLL.

Ce qu'aucun test unitaire ne peut vérifier est validé avec le vrai Mesen2 par deux scripts. Fermez toute fenêtre Mesen2 avant de les lancer :

python tools/mesen2-bridge-check.py <Mesen.exe> example_bomberman-nes/bomber.nes C01A
python tools/dap-smoke.py <WinASM65.Tooling.exe|.dll> <config.json> <source> <ligne>

Le premier vérifie le bridge seul : arrêt avant l'instruction, pas, suppression et effacement des points d'arrêt, pause, RESUMED. Le second pilote l'adaptateur exactement comme VS Code : lancement, point d'arrêt, frame et registres, next, mémoire, console, continue, pause, déconnexion.

Limites connues

  • Instance unique de Mesen2. Si une fenêtre est déjà ouverte, le nouveau lancement lui est transmis et le bridge n'écoute pas sur le port prévu. L'adaptateur détecte la sortie immédiate du processus et le signale.
  • Une trame de latence. En marche, les commandes ne sont servies qu'à la lecture de la manette. Un programme qui ne lit jamais la manette ne répond donc pas à pause.
  • Pile d'appels. Il n'y a qu'une frame, nommée d'après le label le plus proche ; la pile JSR n'est pas reconstituée. stepOut suppose que le haut de la pile est l'adresse de retour.
  • Désassemblage. La vue désassemblage de VS Code n'est pas prise en charge (supportsDisassembleRequest est absent).
  • Banques. La distinction par offset PRG est testée sur des projets construits pour l'occasion, pas encore sur une ROM réelle qui change de banque en cours d'exécution.
  • Fichiers .o. Le build du serveur de langage écrit les .o à côté des sources, comme le build en ligne de commande. Les .symb vont dans un dossier temporaire.
  • Plateforme. Seul le paquet win32-x64 est construit.
