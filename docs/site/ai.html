Tools for AI assistants

WinASM65's assembler, debugger and graphics tools are offered to AI assistants through the Model Context Protocol (MCP). An assistant such as Claude Code, Claude Desktop, GitHub Copilot or Cursor can then build a project, read its errors and listings, run it in the emulator, stop on a breakpoint, inspect registers and memory, and edit graphics, the way a person does in VS Code.

Connecting an assistant

The server is a mode of WinASM65.Tooling, the same program the VS Code extension runs for its debugger and language server: WinASM65.Tooling.exe --mcp. It speaks MCP over its standard input and output.

In VS Code

Nothing to do: with VS Code 1.101 or later, the WinASM65 extension offers the server to the editor's agents (Copilot's agent mode and others). It appears as WinASM65 in MCP: List Servers and starts when an agent first uses one of its tools.

Claude Code

claude mcp add winasm65 -- "C:\Users\you\.vscode\extensions\codewinbzn.winasm65-0.4.0-win32-x64\bin\WinASM65.Tooling.exe" --mcp

Any copy of WinASM65.Tooling.exe works: the one shipped in the extension's bin folder, or a build of the repository (dotnet run --project WinASM65.Tooling -- --mcp).

Claude Desktop, Cursor and other clients

Clients configured with a JSON file take the same command:

{
  "mcpServers": {
    "winasm65": {
      "command": "C:\\path\\to\\WinASM65.Tooling.exe",
      "args": ["--mcp"]
    }
  }
}

The tools

Every tool states what it may do in its MCP annotations: read-only tools only look; the others write files, start an emulator or change its memory. Asking you before a tool runs is the assistant's job, under its own permission settings. A tool that fails returns the reason as text the assistant can act on (a build error with its file and line, a breakpoint on a line with no code, a memory the emulator does not offer).

Debugging

The debug tools drive the same debugger VS Code uses (the debug adapter), inside the server process: launching, breakpoints and stops behave and fail exactly as in the editor. The emulator is the one the project's config.json names (Emulator section), or the one given to debug_launch.

ToolWhat it doesEffect
debug_launchBuilds, starts the emulator with its bridge, sets breakpoints given as file:line, runs, and returns the state if it stopped within waitSeconds.writes
debug_attachConnects to an emulator already running a bridge.writes
set_breakpointsReplaces a file's breakpoints; says where each landed or why it could not.writes
continue, step, pauseRun, step (over, into, out) or stop; return the new state.writes
get_stateWhere and why the program stopped (file, line, its text, routine), registers and flags, and the debug console's output.read-only
read_memoryA hex dump of the CPU's memory or of another memory space of the machine (on the NES: PPU, PAL, OAM, CHR).read-only
write_memoryWrites bytes into a memory space.destructive
evaluateA register, a symbol or $address; a line starting with > is a monitor command.read-only
describe_machineThe system, its memories and views, and the emulator with its capabilities.read-only
debug_stopEnds the session and closes the emulator it started.writes

Graphics

The graphics tools work on the same asset files as the graphics designer in VS Code, with the same validation and the same file format: an assistant and a person can take turns on one asset.

ToolWhat it doesEffect
list_assetsThe assets under a folder with their kind, size and problems.read-only
render_assetDraws an asset as a PNG image the assistant sees: tiles with a palette, palettes, a screen, a map, a metasprite or an animation frame.read-only
get_assetAn asset's JSON and its problems.read-only
update_assetReplaces a JSON asset after validating it; nothing is written when it has errors, which are returned with their JSON path.writes
get_tiles, edit_tilesTile pixels as rows of colour digits, read or drawn.read-only, writes
import_pngA PNG into tiles, palettes and a screen or a metasprite, within the machine's colour limits.writes
export_assetsThe files the assembler includes (.bin, .nam, .rle, .asm with labels) for an asset or a folder.writes
describe_graphics_systemThe machine's graphics rules and master palette.read-only

Protocol details

  • Transport: stdio, one JSON-RPC 2.0 message per line (MCP's stdio transport). Diagnostics of the server go to standard error.
  • Versions: 2025-06-18, 2025-03-26 and 2024-11-05; the client's version is used when the server speaks it.
  • Methods: initialize, ping, tools/list, tools/call. Notifications are accepted and not answered.
  • One debug session at a time; debug_launch ends the previous one.

Checking the server

python tools/mcp-smoke.py <WinASM65.Tooling.exe|.dll> <config.json> <source> <line> [<Mesen.exe>] plays an assistant: it initializes, lists the tools, builds, lists a line, launches the debugger with a breakpoint on that line, waits for the stop, reads the registers and the palette memory, and stops. McpServerTests covers the protocol and every tool against a fake machine.

The asset formats are described on the graphics designer page.
