CPUs and the emulation core

The five instruction sets WinASM65 assembles for, how they are built from one opcode table, how an addressing mode is chosen for a line, and everything that reads those tables: cycle counts, editor documentation, the disassembler. Then the small NMOS 6502 interpreter that runs generated code in the tests.

Five instruction sets

Each CPU is a class implementing ICpuInstructionSet. They form a single inheritance chain: every variant starts from a copy of its parent's opcode map and adds forms to it. The counts below were taken from the built library (cpu.Mnemonics.Count and cpu.Opcodes.Count; each form has its own opcode byte, so forms and opcodes are the same number).

Cpu6502X leaves out, on purpose, the unstable opcodes (ANE/XAA $8B, LXA $AB, SHA, SHX, SHY, TAS) and the duplicate encodings of an instruction that already has one (SBC $EB, the second ANC $2B, the other NOP and JAM codes). Each mnemonic and mode keeps one opcode, which is what lets the disassembler invert the table; a duplicate is shown as .byte.

Choosing a CPU

The CPU comes from the target (each system in the catalog names one), and -cpu or the configuration overrides it; see Targets. The name is turned into an instance by CpuFactory.Create, after Normalize (lower case, hyphens and spaces removed, so W65C02-S works):

Accepted namesInstance
empty, 6502, nmos, nmos6502Cpu6502
6502x, nmos6502x, 6502illegalCpu6502X
65c02, cmosCpu65C02
r65c02, rockwellCpuR65C02
w65c02, w65c02s, wdc65c02CpuW65C02

Anything else throws an ArgumentException naming the canonical list, CpuFactory.Names = 6502, 6502x, 65c02, r65c02, w65c02; the command line reports it as a configuration error. CpuFactory.All returns one instance of each, keyed by canonical name.

The ICpuInstructionSet contract

public interface ICpuInstructionSet
{
    bool IsInstruction(string mnemonic);
    bool IsRelativeBranch(string mnemonic);
    bool IsAccumulatorInstruction(string mnemonic);
    bool TryGetOpcode(string mnemonic, AddressingMode mode, out byte opcode);
    IReadOnlyList<OpcodeEntry> Opcodes { get; }        // every form, sorted
    IReadOnlyCollection<string> Mnemonics { get; }     // upper case
    InstructionInfo ParseOperand(string mnemonic, string operand);
    bool TryOptimizeZeroPage(string mnemonic, AddressingMode currentMode, long value,
        out AddressingMode optimizedMode, out byte opcode, out byte length);
    bool TryCalculateRelativeOffset(long targetAddress, long instructionAddress,
        out byte offset, out string error);
}

ParseOperand returns an InstructionInfo: Mode, Opcode, Length, OperandExpression, SecondOperandExpression (the branch target of BBRn), and HasOpcode, which says whether the CPU really has that form. OpcodeEntry is a readonly struct of Mnemonic, Mode and Opcode.

Opcode tables

The NMOS set is written as literal rows, one byte per addressing mode 0 to 12, with 0xFF meaning "no such form":

// Mode index: IMP=0, ACC=1, IMM=2, ABS=3, ABX=4, ABY=5, ZPG=6, ZPX=7, ZPY=8, IND=9, INX=10, INY=11, REL=12
{ "LDA", new byte[] {0xff, 0xff, 0xa9, 0xad, 0xbd, 0xb9, 0xa5, 0xb5, 0xff, 0xff, 0xa1, 0xb1, 0xff } },

Those rows are read once by FromRows into the shape everything else uses, a map mnemonic → (AddressingMode → opcode), in which a missing key is a missing form. The sentinel stops there: in the map any byte is an opcode, $FF included (it is ISC abs,X on the 6502X). Each subclass overrides one virtual property and builds its map from its parent's with two helpers:

protected virtual Dictionary<string, Dictionary<AddressingMode, byte>> OpcodeMap { get; }

// Cpu65C02.CreateCmosOpcodeMap()
Dictionary<string, Dictionary<AddressingMode, byte>> table = Copy(FromRows(NmosOpcodeTable));
Set(table, "LDA", AddressingMode.ZeroPageIndirect, 0xB2);
Set(table, "BRA", AddressingMode.Relative, 0x80);
…

The other virtual members say which mnemonics take a special operand shape: RelativeBranchMnemonics (the eight NMOS branches, plus BRA on CMOS), AccumulatorMnemonics (ASL LSR ROL ROR, plus INC DEC on CMOS) and BitBranchMnemonics (BBR0–7, BBS0–7 on the Rockwell and WDC parts). Opcodes flattens the map into a list sorted by mnemonic then mode, built once per instance; that list is what the documentation and the disassembler consume.

Choosing the addressing mode

Two steps. ParseOperand decides from the shape of the operand text; the engine's HandleInstruction then decides from the value, when it is known.

1. The shape: ParseOperand

The parser never produces a zero-page mode itself (except (zp) on CMOS): $10 and $0010 are both Absolute at this stage. A is the accumulator only for a mnemonic that has that form, so LDA A reads a symbol called A. The two Cpu65C02 overrides, ParseIndexedIndirectX and ParseIndirect, are the only places a CPU changes the decision.

2. The value: HandleInstruction

  1. Form missing. If HasOpcode is false and the mode has a zero-page twin the CPU does have, that twin is taken with length 2 (STX $10,y has no absolute form: it becomes 96 10). Otherwise: "{mnemonic} does not support {mode} addressing".
  2. Resolved operand, relative. TryCalculateRelativeOffset computes target − (instruction + 2) and refuses anything outside −128..127 ("Relative jump is too big"). BBRn passes instruction + 1 so its displacement counts from the end of its three bytes.
  3. Resolved operand, range. A 2-byte form needs −128..255, a 3-byte form −32768..65535; a value outside is an error and zeros are emitted in its place.
  4. Resolved operand, zero page. TryOptimizeZeroPage: if the mode is Absolute, AbsoluteX or AbsoluteY, the value is 0..255 and the CPU has the zero-page twin, the shorter form is emitted. The relocation is recorded afterwards, so its width follows the bytes actually written.
  5. Pending operand. The opcode and a zero placeholder sized by info.Length are emitted, and a fixup is registered (Assembly pipeline: fixups). The zero-page decision cannot be made, so a forward reference to a zero-page address keeps the absolute form.

One table, four readers

The opcode map is the only description of an instruction set. Everything else is derived from it, so the assembler, the disassembler and the editor cannot disagree about which forms exist.

The cycle table is keyed by opcode byte and knows nothing of mnemonics. In the monitor, AssemblerListingSource reads InstructionDocs (and colours lines with AssemblyLexer), while MonitorSession and ProtocolServer disassemble memory.

Cycle timings

CycleTimings.Of(cpu, mnemonic, mode, opcode, out cycles, out note) gives every form a base count and a note for when it takes longer.

  • The 151 documented NMOS forms read Cpu6502CycleTable.Base(opcode), the execution core's own table. CycleTimingsTests.TheDocumentedNmosCountsAreTheExecutionCoresOwn keeps the two identical.
  • Forms the core does not execute (undocumented opcodes, CMOS additions, Rockwell and WDC bit instructions) take counts written in TryExtra.
  • On a CMOS CPU (cpu is Cpu65C02, which includes the Rockwell and WDC classes) JMP ($nnnn) is 6 cycles instead of 5 and ASL/LSR/ROL/ROR abs,X are 6 plus a page-crossing note.
  • JAM has no count (null): it halts the processor.

InstructionDocs and InstructionDescriptions

Two sources, deliberately split:

InstructionDocs derived

ForCpu(cpu) turns every OpcodeEntry into an InstructionDocumentation: Mnemonic, Mode, Opcode, Length (Disassembler.ModeLength), Syntax (SyntaxFor), Cycles, CycleNote, CyclesText. Cached per CPU instance in a ConditionalWeakTable. Also ForMnemonic, TryGet, MnemonicsFor, IsMnemonic.

InstructionDescriptions written

The prose: for each mnemonic, its full name ("Load Accumulator"), a one-sentence summary and the flags it changes ("N Z"). RMBn, SMBn, BBRn, BBSn are generated from the digit. InstructionDescriptionsTests.EveryMnemonicOfEveryCpuIsDescribed checks coverage.

The language server builds its instruction hover from both (HoverCard.Instruction): the description gives the title, summary and @flags; the form the line assembled to gives @mode, @cycles and @bytes; the table lists every form of the mnemonic on the project's CPU, with a ◀ on the one used. The assembled form is found by matching the listing row's first byte and length against InstructionDocs.ForCpu and checking the mnemonic is written on the line.

InstructionDocs.MnemonicsFor(cpu) is also what TextFormat/AssemblyLexer classifies mnemonics against when it colours a line.

The disassembler

new Disassembler(cpu) inverts cpu.Opcodes into an opcode → OpcodeInfo(mnemonic, mode, length) index, and throws at construction if one opcode maps to two different forms: refusing to start is preferred over disassembling wrong. Disassemble(address, memory, offset) returns a DisassembledInstruction:

  • an opcode not in the table gives IsKnown = false and the text .byte $xx, never a guess ($02 on an R65C02 for example);
  • operands are rendered by RenderOperand in the syntax the assembler accepts, upper-case hexadecimal; the accumulator form is rendered with no operand;
  • branches show their target address and fill TargetAddress; BBRn shows $zp,$target (bytes 3F 10 FD at $8000 give BBR3 $10,$8000);
  • a buffer too short for the instruction gives the bytes available while Length stays the instruction's length.

Because the zero-page form is kept as it is, assembling a disassembly gives back the same bytes; DisassemblerTests checks that round trip. The monitor uses the disassembler for memory views (MonitorSession, ProtocolServer); see Monitor.

The execution core

Execution/Cpu6502Core is a small NMOS 6502 interpreter. It exists to run code the toolchain generates, such as the relocating stub built by TextFormat/RuntimeBlock, instead of only comparing its bytes. It executes the processor and nothing else: no video, no hardware, no real-time clock.

Cycles

Each instruction costs Cpu6502CycleTable.Base(opcode), plus one when a branch is taken, plus one more when a branch or an indexed read crosses a page. Indexed stores never pay the crossing. Cpu6502Core.GetBaseCycles(opcode) exposes the base count; an opcode the core does not implement reads 0.

What it does not do

  • It executes the 151 documented NMOS opcodes only (the opcodes with a non-zero base count are exactly the Cpu6502 table). Any other opcode throws NotSupportedException; there is no 65C02 or undocumented-opcode execution.
  • ADC/SBC with the decimal flag set throw NotSupportedException rather than computing a wrong result.
  • Peek16 does not reproduce the NMOS page wrap of JMP ($xxFF).
  • Push/Pull use SP itself as the address, so the stack lives at $00xx rather than $01xx; and zp,X/zp,Y add the index without wrapping inside page zero. Neither matters to the generated stubs it runs, but both matter to anyone pointing it at arbitrary code.

The core's own documentation describes it as a deterministic machine a debugger could be pointed at without an emulator; that connection does not exist yet.

Adding an instruction or a CPU

  1. Derive from the closest CPU, build the map from a Copy of the parent's and Set the new forms; override OpcodeMap, and the mnemonic sets if the new instructions branch or take an accumulator.
  2. Register the name and its aliases in CpuFactory.Create and CpuFactory.Names.
  3. Give every new mnemonic a line in InstructionDescriptions, and its cycle counts in CycleTimings.TryExtra; the coverage tests walk every CPU in CpuFactory.All and fail on a missing description or count.
  4. A new addressing mode also needs ParseOperand (or an override), Disassembler.ModeLength and RenderOperand, InstructionDocs.SyntaxFor, AddressingModes.Describe, and possibly AssemblerEngine.HandleInstruction.
