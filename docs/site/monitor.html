WinASM65 › Debugging

The monitor

A terminal program that drives a running emulator. It reads and writes the machine's memory, sets breakpoints, steps, assembles and places code, and shows the source with what each line assembled to. It talks to Mesen2 (or MesenCE) through a small Lua script, the bridge, over a local TCP socket. This page explains how it is built, for someone about to change it.

Architecture

One rule shapes the whole design: every action is a command line into MonitorSession. The terminal UI, the line prompt and the tests all go through MonitorSession.Execute(string), which returns lines of text and never touches the console. A key in the TUI cannot do something a typed command cannot. And the session talks to an emulator only through IMemoryBackend, so the monitor can be tested without one.

The same session is used by the line prompt (Program.RunRepl), which prints whatever Execute returns. WinASM65.Tooling's debug adapter uses the same backend and source map, but drives the backend directly rather than through MonitorSession.

MonitorSession

MonitorSession owns a backend, a Disassembler for the session's CPU, a UnitLibrary, a ProjectBuilder and, optionally, an EmulatorLauncher. Execute never throws for a bad command: a failure becomes an ERR … line, because a monitor that dies on a typo cannot be used to find out what the typo was. Verbs are case-insensitive.

Backends

IMemoryBackend (in Monitor.Core) is the only contract between the monitor and an emulator: name and version, IsRunning, IsConnected, RamRefreshMode, Read/Write, Pause/Resume/Step/Reset, AddBreakpoint/ClearBreakpoints, SaveState/LoadState, and a RamChanged event. Anything a backend may or may not have is a separate, optional interface, tested with as:

BridgeMemoryBackend

  • Handshake. The constructor sends PING and takes the first two words of the answer as name and version (OK Mesen2 2.1.1), then looks the pair up in ExecutionCapabilities. It then sends STATUS; a bridge that answers ERR (MesenCE) is recorded as one that does not report run state.
  • Chunking. Reads and writes go out in 256-byte requests. MesenCE kills a script that stays too long in one pass, and the bridge loops byte by byte.
  • A RAM cache. A private 64 KiB copy, updated from PUSH RAM lines and from the monitor's own writes, so a pushed change can be shown without re-reading.
  • A polling fallback. A background thread reads $0000–$07FF every 250 ms and raises RamChanged with the difference, but stays quiet within 500 ms of a push and while the machine is stopped. RamRefreshMode reports RAM: Live when pushes are arriving, RAM: Polling otherwise, and RAM: Stopped when polling is off. The debug adapter and the tests turn polling off.
  • Errors keep the bridge's words. An ERR reply becomes a MonitorException whose message is the verb plus the bridge's reason, e.g. PAUSE: PAUSE unavailable: MesenCE 2.2.1 does not expose emu.pause.
  • Reconnect. Reconnect() disposes the client, retries for up to 15 s, re-subscribes to pushes, and repeats the handshake.

DummyBridgeBackend

When no bridge answers, the monitor still starts, on DummyBridgeBackend: name Dummy 0.0, reads return zeros, writes and execution commands are ignored, IsConnected is false. It does not implement IExecutionAdapter, so its capability set is None and the status line says caps: nothing measured.

What Program.Main does, in order:

  1. Sets the console to UTF-8 (SharpConsoleUI draws box characters directly) and parses the options.
  2. With --mesen, starts the emulator through EmulatorLauncher; exit code 3 if it cannot. Without it, EmulatorLauncher.FromProjectConfiguration reads an optional "Emulator": { "Path": … } from config.json in the working directory. That generic launcher passes the ROM (Output.ObjectFile) as the only argument and loads no bridge.
  3. BridgeConnector.TryConnect(port) retries the connection every 250 ms for up to 15 s (DefaultTimeoutMs = 15000). If nothing answers, it writes the reason to stderr, "… Starting without a bridge.", and the monitor continues on a DummyBridgeBackend.
  4. Builds one Cpu6502, shared by the session and the listing source so they agree on mnemonics, lengths and cycles, then a MonitorSession rooted in the working directory.
  5. Runs ShellRunner.Run (TUI) or RunRepl. On every way out, the emulator it started is killed and waited for, so Mesen never outlives the monitor.

The bridge and its protocol

The bridge is a Lua script running inside the emulator. It opens a TCP server on 127.0.0.1, accepts a single client, and turns each text line into calls on the emulator's emu.* API. All the logic stays on the .NET side, so the protocol can be typed by hand over telnet. The constants live in Protocol/MonitorProtocol.cs.

Lines

  • Every request is one ASCII line. Every reply is one line that starts with OK or ERR <reason>. Nothing fails silently.
  • The bridge may also send unsolicited lines that start with PUSH. They are never the reply to a request.
  • Requests are answered in order and carry no id, so the client allows only one request in flight (ProtocolClient.Send holds a lock).

Two threads on the .NET side

ProtocolClient owns the socket. A background thread (monitor-receiver) reads every line: lines starting with PUSH go to the PushReceived event, everything else into a reply queue. Send writes the request and waits on the queue. Without this split, a push arriving between a request and its reply would be taken for the reply. Connecting times out after 5 s; a read blocks for at most 30 s.

Bounds

The bridge is a synchronous script inside the emulator, so an unbounded request would freeze the emulator. The bounds are part of the contract and are tested.

Breakpoints and stepping on Mesen2

Mesen2's emu.breakExecution, emu.resume and emu.step only work inside an event callback, never from the script body. bridge_mesen2.lua is therefore built entirely from callbacks registered in start():

CallbackRole
on_tick on eventType.inputPolledOnce per frame while the machine runs: accept the client, send PUSH RAM, read a command. If there is one, emu.breakExecution(), answer it and up to 63 more queued ones, then resume (or pause, step or reset if asked).
serve_stopped on eventType.codeBreakFires after a breakpoint or a step. Pushes STOPPED, then serves commands in a blocking loop (serve_blocked, 0.5 s receive timeout) until RESUME, STEP or RESET. No frame callback fires while the machine is stopped, so this is the only place a stopped machine can be served.
on_reset on eventType.resetMarks the reset as done. Breakpoints are ignored from the moment a reset is requested until this fires, so the old program cannot hit one on its way out.
Memory callback, callbackType.write over $0000–$FFFFRecords every CPU write into the dirty set that becomes PUSH RAM.
Memory callback per breakpointexec: records the stop and halts. read/write: only log the access; they do not stop the machine.
  • Stopping before the instruction. emu.breakExecution stops at the end of the current instruction, so the instruction under the breakpoint would already have run. The exec callback calls emu.step(1, cpuCycleStep) instead, which stops right after the opcode fetch: PC, registers and memory are as they were before the instruction.
  • Stepping. A step needs a running machine. STEP is answered OK, then step_once resumes and calls emu.step(1, stepType.step); the next codeBreak pushes STOPPED reason=step.
  • A breakpoint at the current PC does not fire until the CPU comes back to it: Mesen2 treats the instruction as already reached.
  • The client leaves. If the monitor disconnects while the machine is stopped, the bridge calls emu.stop(0).

A breakpoint hit, from the debugger's request to the resume. The front end here is the VS Code debug adapter (DebugSession), which is what subscribes to Stopped; the TUI does not.

Setting the breakpoint happens while the machine runs: on_tick breaks execution, answers BREAK SET, and resumes within the same frame. The adapter then maps pc and prg back to a source line with the source map; if another bank at the same CPU address is executing, it resumes without reporting the stop.

Capabilities

What a host can do is declared, never probed. ExecutionCapability (Abstractions) is a flag set: MemoryRead, MemoryWrite, CpuState, Pause, Resume, Reset, StepInstruction, BreakpointExecution, WatchpointRead, WatchpointWrite, StateSaveLoad, with the composites Memory and FullControl. ExecutionCapabilities.For(name, version) answers from a table of builds that were measured; any other name or version gets None.

MesenCE's bridge refuses PAUSE, RESUME, STEP, BREAK and RESET by name, with what was measured on 2.2.1: emu.pause does not exist; emu.resume and emu.step refuse calls outside a callback; emu.addMemoryCallback refuses every function; emu.reset is reserved for manual validation. The shell uses the same flags: F7, F8, F9 and F10 each name the capability they need (ShellKey.Requires), the help screen marks keys the machine cannot honour, and pressing one shows a refusal from ShellCapabilities instead of sending a command.

The other probe scripts in Bridge/ are not bridges: probe_mame.lua reports what MAME's Lua can do as MPROBE key=value lines for MameCapabilityTests, and spike_m0.lua is the original MesenCE 2.2.1 capability spike.

Listings and the source map

The editor's gutter (address, bytes, cycles) comes from the assembler's own listing, through a narrow seam, IListingSource (Monitor.Core/Shell/ListingSource.cs). The panes know only its types: ListingRow, EditorRow, and ListingToken, a run of text tagged with a ThemeRole name rather than a colour.

TypeRole
AssemblerListingSourceLists one file with the library's SourceListingService. Assembles again on every call (nothing is cached). Cycles come from the documented instruction form whose opcode is the row's first byte; a data byte gets none. An assembly error yields the reason and no rows.
ProjectListingSourceLists a file of a project that has just been built, using ProjectSession.ProjectSymbols, so names defined in another unit are not reported as undefined.
ProjectConfigLocatorDecides which config.json governs the open source: the nearest one, searching upwards to the session directory, that declares the file as an input. An unreadable configuration still counts as governing, so BUILD can report it.
ListingSourceFactoryCreates the listing source for a given CPU and directory.

The source map (Monitor.Core/Debugging/) goes the other way, from addresses to lines. SourceMapBuilder.Build takes a project build run with CaptureListing and produces MappedLines: CPU address, length, PRG offset, file and line. The PRG offset is computed the way the bytes travelled: offset in the unit's object file, plus where that file sits in the image, minus the iNES header. SourceMap answers AtLine, AtAddress, Resolve(pc, prgOffset) (with an ambiguous flag when banks share an address), NearestLabel and TryNearestEmittingLine. In the current code it is used by the debug adapter (WinASM65.Tooling/Dap/DebugSession.cs), not by the TUI.

Units and project builds

A monitor's distinctive job: assemble a routine once and place it anywhere without assembling it again.

  • RelocatableUnit keeps the relocatable modules an assembly produced. FromSource assembles a file and refuses one with no .export and no .import, since it produces no module. PlaceAt(address) runs the WinASM65 linker with AddressShift = address − NaturalOrigin and checks that the image landed where it was asked to. A unit with several blocks moves as a whole: blocks at $8000/$9000 placed at $3000 land at $3000/$4000.
  • UnitLibrary holds the units by name and implements ASSEMBLE, LOAD and UNITS. LOAD refuses units over 16 KiB, writes the block, reads it back and compares byte by byte, and answers OK $3000 24 byte(s), 3 site(s) or names the first mismatch. The read-back is the only proof the code is really at the address named.
  • ProjectBuilder implements BUILD: it opens a ProjectSession on the configuration (resolved against the session directory), builds, and turns every failure, including missing files and bad JSON, into ERR lines. It keeps the last session and result so the shell can list project files and find the built image.

See Modules, linker, viewer for the module format and Projects and segments for config.json.

Known limits

  • Read and write watchpoints on Mesen2 only log the access; they do not stop the machine.
  • The MesenCE bridge listens on the fixed port 45678, whatever --port says.
  • A monitor that started on DummyBridgeBackend stays on it: CONNECT calls the dummy's Reconnect, which does nothing.
  • The header comment of bridge_mesen2.lua still describes a headless --testRunner launch; BridgeLauncher now opens the normal Mesen2 window (screenshot).
  • docs/monitor.md (French) predates Mesen2 support and the project split: it describes MesenCE only, and its test counts are out of date.
  • The plugin contract is defined and tested (PluginContractLoadingTests), but the monitor does not load plugins yet.
