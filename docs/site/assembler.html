The assembly pipeline

How one source file becomes bytes: the entry points, the engine that reads the source line by line, the regex dispatcher that decides what each line is, the expression evaluator, the directives, the fixups that patch forward references, and what comes out at the end. Written for a developer who is about to change the assembler.

This page is about the machinery. The language it accepts (label forms, number formats, every directive with examples) is described in the syntax reference; the instruction sets and how an addressing mode is picked are on CPUs and emulation core.

The pipeline at a glance

WinASM65 reads a source once, top to bottom. Each line is classified by a chain of regular expressions and handed to a handler that emits bytes, defines a name, or both. A value that is not known yet (a forward reference) is written as a zero placeholder and recorded; it is patched as soon as the name it waits for is defined, and once more at the end of the source. There is no second reading of the text: the "second pass" is the resolution of those recorded fixups.

Entry points

Program.Main wires the command line application with its five collaborators, all behind interfaces so tests can replace them:

CommandLineApplication application = new CommandLineApplication(
    new AssemblerFactory(),
    new JsonConfigurationReader(),
    new BinaryCombiner(),
    new SystemConsoleOutput(),
    new ExecutablePublisher());
return application.Run(args);

CommandLineApplication.Run

The first argument may be a verb (link, archive, view, geos, basic), each with its own method; see Modules, linker, viewer and Targets. Otherwise the run is an assembly, driven by -f, -o, -l, -t/-target, -cpu, -format and -c. In order, it:

  1. reads the configuration (-c) through IConfigurationReader; JsonConfigurationReader deserializes a ConfigFile with Newtonsoft.Json and throws on a missing path, which Run turns into a configuration error and exit code 1;
  2. resolves the target with TargetResolver.Resolve (configuration, then -t, -cpu, -format) and creates the CPU with CpuFactory.Create(target.CpuName);
  3. collects the predefined symbols: the target's hardware names (when DefineHardwareSymbols is set) plus the names of declared memory regions, and activates the memory map (MemoryMapScope.Activate) so .org and .res can be checked against it (Projects and segments);
  4. with -f: assembles that file, then writes it as a .w65 module or hands the bytes to ExecutablePublisher unless the format is raw bin;
  5. with a configuration that lists Input units: runs MultiSegmentOrchestrator over them, then combines and publishes Output.

Any failing step prints its diagnostics to standard error and returns 1.

Inside AssemblerEngine

AssemblerEngine implements IAssembler (for callers) and IAssemblyContext (for directive handlers). All of its collaborators are constructor parameters with defaults, so a test can inject any of them:

public AssemblerEngine(
    ICpuInstructionSet cpu = null,             // Cpu6502
    ITokenizer tokenizer = null,               // Tokenizer
    IExpressionEvaluator evaluator = null,     // ExpressionEvaluator
    IScopeManager scopeManager = null,         // ScopeManager
    IBinaryEmitter emitter = null,             // BinaryEmitter
    IListingService listingService = null,     // ListingService
    IDiagnosticReporter diagnostics = null,    // DiagnosticReporter
    IDirectiveDispatcher directiveDispatcher = null, // CreateDefaultDispatcher()
    IDictionary<string, long> predefinedSymbols = null,
    ushort? defaultOrigin = null,
    bool reportUndefinedSymbols = true,
    string sideFileDirectory = null)

Assemble calls Reset() first, so one engine can assemble repeatedly. It then applies the default origin and predefined symbols, pushes the file's lines and runs ProcessFileStack. The loop reads from the current SourceFileState (a path and a line counter); .include calls PushSourceFile, which stacks the current file and continues in the new one, and the outer loop pops back when it runs out. .end calls StopAssembling().

For each raw line, ProcessFileStack:

  1. sends the raw text to the listing (PrintLine) and increments the line number;
  2. trims it and removes the comment with SourceText.StripComment; a blank result ends the line;
  3. while a macro is being defined, appends the line to the macro body instead of parsing it (unless it is .endmacro/.endm or another .macro);
  4. otherwise calls ParseLine.

The line dispatcher

ParseLine records the line's start address (what * means in an expression), drops lines of an inactive conditional branch (except the conditional directives themselves), buffers lines inside a .rep block, and passes the rest to ParseLineBody. There, the line is tested against a fixed sequence of patterns. The first match wins, so the order is part of the language.

Why the order matters:

  • Anonymous labels first. A line of only - or + characters, optionally followed by a statement (- lda #1), defines an anonymous label; the rest of the line is fed back into ParseLineBody.
  • EQU before instructions. COUNT EQU 4 would otherwise look like a label followed by a three-letter mnemonic.
  • label .res n before directives. It is a reservation that names the space, not a label in front of a directive (HandleMemReserve advances CurrentScope.MemArea and emits nothing).
  • Label + directive before directive. Data: .byte $AA has to define Data at the address the bytes go to, then run the directive; the label is defined first.
  • Bare labels are anchored. LabelDeclareRegex only matches a label alone on its line, so Loop: nop reaches InstructionRegex, whose optional label group defines Loop.
  • Macro calls last. MacroCallRegex accepts any identifier with arguments. A macro whose name fits InstructionRegex (three letters plus an optional digit) is caught there: HandleInstruction looks the name up in the macro table before treating it as a mnemonic.

The three-letter ambiguity. InstructionRegex's label group is greedy, so lda Mid parses as label lda, mnemonic Mid. HandleInstruction checks whether the "label" is a mnemonic of the current CPU and swaps the two back, keeping the operand as written.

Labels, scopes and names

The symbol table

ScopeManager keeps a list of LexicalScopeData, index 0 being the global scope. Each holds a SymbolTable (name → long), the UnsolvedSymbols waiting in that scope, and the MemArea counter used by .res. Both dictionaries compare names with StringComparer.OrdinalIgnoreCase: symbols are case-insensitive, and the spelling the source used is kept for relocations.

  • { and } push and pop a scope (at most 255 levels). TryResolveSymbol walks from the current scope down to the global one. When a scope closes, its unsolved entries are merged into the parent.
  • AddSymbol(label, value, replaceIfExist, out error) refuses a duplicate with LABEL_EXISTS unless asked to replace. Labels do not replace (except, once, a name the target predefined); = and .set constants do; EQU replaces only with the same value (CONSTANT_REDEFINED otherwise).
  • The engine also keeps its own list of the labels the source defined (_sourceLabels): only a label is an address, and that list is what becomes a module's symbol table.

Local and anonymous labels

Neither has its own table: the engine rewrites them into ordinary, generated names.

WrittenStored asMechanism
@loop after global label MainMain@loopDefineName prefixes the current scope: the last global label that took an address (_currentGlobal).
@loop inside a macro expansion or .rep iteration__m7@loopBeginExpansion pushes a fresh counter; the innermost expansion is the scope, so a macro can be used twice.
-, --, +…__anon_m1_0, __anon_p1_3…DefineAnonymous counts definitions per direction and run length; - and -- are different names, as in asm6.

References are rewritten the same way before evaluation by ExpandNames: an operand that is only a run of - becomes the latest backward label of that length, a run of + becomes the next forward one (not yet defined, so it is a forward reference like any other), and every @name token gets the current scope prepended. The tokenizer accepts Scope@name as one identifier for exactly this reason. Generated names are never exported to .symb, and one left undefined is reported in source terms (LOCAL_LABEL_UNDEFINED, ANON_LABEL_NOT_FOUND), even in a multi-file build.

Expressions

Every operand and directive argument goes through AssemblerEngine.ResolveExpression(expr, addrMode, isLogical), the single place where an evaluation error is reported.

Tokenizer

Tokenizer is one compiled regex whose named groups map to TokenType. The alternatives are ordered: OR/AND/TRUE/FALSE match whole words only (so origin is a name), character literals come before numbers, and % is a binary prefix only where an operand is expected (after a value it is modulo: 7%10). The last alternative, (?<invalid>[^\s]+), catches anything else so it becomes an error instead of being silently dropped. Numbers are 123, $FF, %1010; see the syntax reference for the full list.

Evaluator

ExpressionEvaluator.Evaluate first runs CheckShape (operands and operators must alternate, parentheses must balance). It then converts literals, and looks every identifier up through ISymbolResolver (the ScopeManager). Each identifier is recorded in UsedSymbols whether or not it resolves. If any name is undefined, evaluation stops there and returns a pending result listing the missing names: there is never a partial value. Otherwise a shunting-yard pass computes the value; an operator is unary when it is first or follows another operator or an opening parenthesis.

A result also carries its Expression text (already rewritten, so a pending expression re-evaluated later still means what it meant on its line), its Location, and a Role. The evaluator never sets the role: lda #$05 and lda label are the same expression, and only the addressing mode tells them apart. ResolveExpression attaches it with RoleFor(mode); data directives use ExpressionRole.Data, and conditions (isLogical) get None.

Directives

A directive is a class implementing a two-member interface, registered by name in a dispatcher:

public interface IDirectiveHandler
{
    string Name { get; }                       // ".byte", with the dot
    void Execute(string argument, IAssemblyContext context);
}

IAssemblyContext is the engine as a handler sees it: Emitter, ScopeManager, ExpressionEvaluator, ListingService, Diagnostics, Cpu, CurrentLocation, the conditional, repeat and macro state, and the operations ResolveExpression, ParseLine, PushSourceFile, StopAssembling, DeferAssertion, BeginExpansion/EndExpansion.

DirectiveDispatcher stores handlers in a case-insensitive dictionary. RegisterAlias(alias, target) maps another spelling to the same handler instance. DispatchDirective lower-cases the name and reports UNKNOWN_DIRECTIVE when nothing is registered. The default set is built in AssemblerEngine.CreateDefaultDispatcher, and AssemblerEngine.DefaultDirectiveNames lists it for tools that need the names.

FileDirectives (handler)
StandardDirectives.cs.org (Org), .memarea (MemArea), .incbin (IncBin), .include (Include), .byte, .word, .macro, .endmacro, .if, .ifdef, .ifndef, .elseif, .else, .endif, .rep, .endrep, .end, and .equ/.set on their own (NamedValue: always an error, since the named form is caught by the dispatcher)
ExtendedDirectives.cs.asciiz, .lobytes/.hibytes (ByteTable), .dsb/.dsw (Fill), .res without a label (Reserve), .pad, .align, .error, .warning, .assert
Modules/ModuleDirectives.cs.export, .import (see Modules)
aliases.db, .byt → .byte; .dw, .addr → .word; .endm → .endmacro; .rept → .rep; .endr → .endrep; .ds, .fill → .dsb

Some forms never reach the dispatcher because a line pattern catches them first: *= expr, NAME EQU v, NAME .set v and label .res n.

Data: DataEmitter

.byte, .word, .asciiz and .lobytes/.hibytes split their arguments with SplitArguments; a quoted argument goes through DataEmitter.TryEmitString, anything else through DataEmitter.Emit(context, expression, width):

  • Resolved: a value outside −128..255 (byte) or −32768..65535 (word) is refused and a zero emitted in its place; otherwise the value is emitted and, if the expression read a symbol, a relocation of type Data8/Data16 (or LowByte/HighByte) is recorded.
  • Pending: a zero placeholder of the right width is emitted and an UnresolvedExpr registered, exactly as for an instruction operand.

.lobytes and .hibytes just wrap each argument in <(…) or >(…) before emitting it.

Values that must be known now

A directive whose argument decides how many bytes are emitted or where they go cannot use a placeholder. .dsb/.dsw, .res, .pad, .align and the .incbin offset/length use DirectiveArguments.TryResolveNow, which reports "… known at this point (undefined: …)". .org, .memarea, .rep, .if and .elseif report Undefined symbol when their expression is pending. .ifdef/.ifndef test whether the name is defined at that line.

Conditionals

ConditionalState is a stack of frames (ParentActive, Taken, Active, SeenElse), at most 255 deep. ParseLine asks ShouldAssembleCurrentLine() and skips the line unless it is itself a conditional directive. An .if inside a skipped branch pushes a false frame without evaluating its condition, and an .elseif evaluates its condition only when its frame is live and no earlier branch was taken, so a dead branch may name symbols that do not exist.

Macros

  1. .macro name p1, p2 creates a MacroDefinition and sets CurrentMacroBeingDefined. A nested .macro is refused (NESTED_MACROS), a duplicate name too (MACRO_EXISTS).
  2. ProcessFileStack stores the following lines, trimmed and without comments, in the definition until .endmacro/.endm.
  3. A call (HandleMacroCall) opens an expansion (BeginExpansion), splits the arguments with SplitArguments, folds surplus arguments into the last parameter, replaces each parameter as a whole word ((?<![\w@])param(?![\w]), case-insensitive), and sends each line through ParseLine. A macro with parameters called without arguments is an error.

Repetition

.rep n evaluates n immediately and sets RepeatState.IsInRepeatBlock; ParseLine then buffers every line until .endrep/.endr. EndRepDirectiveHandler replays the buffer n times, each iteration in its own expansion so @labels inside are distinct. .rep blocks do not nest (NESTED_REP).

Instructions

HandleInstruction is the busiest handler. In short:

  1. a name that is a macro is expanded instead;
  2. the label/mnemonic swap described above, and the label (if any) is defined at the current address;
  3. an unknown mnemonic is UNKNOWN_MNEMONIC and emits nothing;
  4. Cpu.ParseOperand picks the addressing mode from the operand's shape; a form the CPU lacks falls back to its zero-page twin when there is one (STX zp,Y), otherwise UNSUPPORTED_ADDRESSING_MODE;
  5. implied and accumulator forms emit one byte; BBRn/BBSn go to EmitBitBranch;
  6. the operand is evaluated. Resolved: branch offset, range checks, zero-page shrinking, emission, relocation. Pending: opcode plus a zero placeholder sized by the form, and a fixup.

How the mode and the opcode are chosen, including zero page versus absolute, is detailed on CPUs: choosing the addressing mode.

Forward references and fixups

Two records in Symbols/SymbolTypes.cs carry everything that could not be finished:

RecordOne perFields
UnresolvedExprplaceholder in the bufferExpr (rewritten text), NbrUndefinedSymb (names still missing), Position (address minus OriginAddress: where to patch), BufferOffset, Type (Byte/Word), AddrMode, Location. Kept in ScopeManager.UnsolvedExprList, keyed by Position.
UnresolvedSymbolmissing nameExprList (positions of placeholders waiting for it), DependingList (constants waiting for it). For a pending constant: its Expr and NbrUndefinedSymb.

ScopeManager.ResolveSymbols runs after every label definition (named or anonymous) and once more from Complete. For each unsolved global name that now has a value, it decrements the counter of every waiting constant and placeholder; at zero, the expression is evaluated again and, for a placeholder, the engine's PatchResolvedExpression writes the bytes:

  • relative branches (Relative, and the second operand of BBRn) recompute the displacement from the instruction address and may still fail with "Relative jump is too big";
  • byte and word fields are range-checked, then written with PatchByte/PatchWord, and the matching relocation record is marked resolved.

An error found at this point (a branch out of range, a value too wide, a division by zero) is reported at the Location stored in the pending expression, not at the end of the file.

Consequences worth knowing

  • Width is fixed when the placeholder is emitted. A forward reference to a zero-page address keeps the absolute form: lda later followed by later = $10 assembles to AD 10 00, while the same reference made after the definition gives A5 10.
  • Constants are not a trigger. Defining a constant with = does not call ResolveSymbols; its waiters are served at the next label or at the end.
  • Deferred assertions. An .assert whose expression is pending is stored with DeferAssertion and checked in Complete.

What is left at the end

ReportStillUndefinedSymbols runs after the last resolution. A generated name (local or anonymous) left undefined is always an error. Any other name is an error Undefined symbol: NAME. Define it, or declare it with .import when another module provides it., located at the first relocation that reads it, unless ReportUndefinedSymbols is off or the name was declared with .import.

Across files

In a configuration build every unit is assembled with ReportUndefinedSymbols = false. A unit that still has pending work writes it to side files next to its source: .Unsolved (the UnsolvedSymbols dictionary) and .UnsolvedExpr (the UnsolvedExprList), as JSON. MultiSegmentOrchestrator then, for each such unit, creates a fresh engine, reloads the object file into its emitter, reloads both files, injects the .symb of every declared dependency into the global scope, calls ResolvePendingSymbols(), fails with Undefined symbol if anything remains, rewrites the object file and deletes the two side files. The dependencies are declared in config.json; see Projects and segments.

Diagnostics

Core/Diagnostic.cs holds the whole model:

    public SourceLocation Location { get; }     // FilePath + LineNumber

Output

BinaryEmitter

One flat List<byte> and two addresses. EmitByte/EmitWord/EmitBytes append and advance CurrentAddress; words are little-endian. PatchByte/PatchWord/PatchBytes overwrite at a buffer position. Setting OriginAddress (what .org does) also appends an EmitterOrigin(bufferOffset, address) to Origins: there is one buffer, and the list of origins is how a module is later cut into one segment per .org. SaveToFile writes the raw buffer.

Relocation records

Every emitted field whose value depends on a symbol, resolved or not, gets a RelocationRecord: segment, buffer offset, address, width, type, the symbols read (the first is TargetSymbol), source file and line, expression text, and, once known, the value written. A field that read no symbol records nothing. In a direct build they are informational; they become the relocations of a .w65 module (Modules).

Listings

The engine never formats a listing. It reports fragments to an IListingService: the raw text of a line (PrintLine(string)), what the line produced (PrintLine(LineType, value)), and EndLine().
