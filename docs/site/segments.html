Projects and segments

A config.json describes a program made of several sources: the units to assemble and which names each may take from the others, the files to put end to end into the final image, and optionally the target and the emulator. This page explains the file, the two-phase build behind it, and the classes that run it.

The build at a glance

A project build has two stages that know nothing about each other. The Input stage assembles each unit into its own object file, already placed at its real address by its own .org; names cross from one unit to another through small JSON side files. The Output stage then concatenates files, object files and plain binaries alike, padding each one to a declared size, and hands the result to the target's format.

The command line runs it as WinASM65 -c config.json, optionally with -l for listings and -t, -cpu, -format to override the target. The editor tools run the same build through ProjectSession. Every key of the file is listed in the config.json reference below.

config.json reference

This section lists every key the code reads from config.json, with its type, its default and what it does. Two different readers go through the file:

  • Target, Input and Output are read by JsonConfigurationReader with Newtonsoft.Json into a ConfigFile (Segments/SegmentModels.cs). Key names are matched without regard to case ("input" works), and a key the classes do not declare is ignored silently, so a misspelt key ("Sytem") is not reported: the field just keeps its default. A value of the wrong type stops the run, for example Could not convert string to boolean: yes. Path 'Target.Ines.Battery'.
  • Emulator is not part of ConfigFile. The monitor and the debug adapter read it through one class, EmulatorConfiguration.Read (Monitor.Core/Emulators), with System.Text.Json; its key names are matched without regard to case too. The command line still parses the whole file, so a syntax error inside Emulator (an unescaped \ in a Windows path, say) fails the build too.

Relative paths. On the command line (WinASM65 -c config.json) every path of Input and Output is relative to the current directory: run it from the project directory, as compile.bat does. Everything built through ProjectSession (VS Code build task, debug adapter, language server, the monitor's BUILD) resolves them against the directory of config.json. Emulator.Path is always relative to the directory of config.json.

A complete example

Every key of a NES project, for Star Catcher (example_star_catcher). This configuration builds the same 24,592-byte star_catcher.nes as the committed one (byte for byte; checked with the Release build), the difference being that the iNES header comes from the Ines section instead of from src/header.asm, which is no longer an input. The regions are declarations only: the two that hold code (PRG, VECTORS) match the .orgs of the sources, ZEROPAGE holds the game's variables (.memarea $0000 and .res), OAM is the page the game copies to the PPU every frame, and RAMCODE, which the game does not use, shows the rw type and the Load key. JSON has no comments, so the explanations are in the tables below.

{
  "Target": {
    "System": "nes",
    "Cpu": "6502",
    "Format": "ines",
    "LoadAddress": "$C000",
    "DefineHardwareSymbols": true,
    "Ines": {
      "PrgBanks": 1,
      "ChrBanks": 1,
      "Mapper": 0,
      "Mirroring": "horizontal",
      "Battery": false
    },
    "Hardware": {
      "Model": "nes",
      "VideoStandard": "ntsc"
    },
    "Regions": [
      { "Name": "ZEROPAGE", "Address": "$0000", "Size": "$100",  "Type": "bss" },
      { "Name": "OAM",      "Address": "$0200", "Size": "$100",  "Type": "bss" },
      { "Name": "RAMCODE",  "Address": "$0300", "Size": "$80",   "Type": "rw", "Load": "$E000" },
      { "Name": "PRG",      "Address": "$C000", "Size": "$3FFA", "Bank": 0, "Type": "ro" },
      { "Name": "VECTORS",  "Address": "$FFFA", "Size": "6",     "Type": "ro" }
    ]
  },
  "Input": [
    {
      "FileName": "src/game.asm",
      "OutputFile": "src/game.o",
      "Dependencies": []
    },
    {
      "FileName": "src/vectors.asm",
      "Dependencies": ["src/game.asm"]
    }
  ],
  "Output": {
    "ObjectFile": "star_catcher.nes",
    "Files": [
      { "FileName": "src/game.o", "Size": "$3FFA" },
      { "FileName": "src/vectors.o" },
      { "FileName": "chr/tiles.chr" },
      { "FileName": "chr/floor.chr" }
    ]
  },
  "Emulator": {
    "Name": "mesen2",
    "Path": "C:\\Emulators\\Mesen2\\Mesen.exe"
  }
}

Most of the Target section repeats what "System": "nes" already implies (CPU, format, hardware symbols, one PRG and one CHR bank, mapper 0, NTSC); it is spelled out here to show the keys. Mirroring is the exception: the nes default is vertical, and the game scrolls vertically, which needs horizontal mirroring. The nes system predefines hardware symbols (PPUCTRL, OAMDMA, JOY1…) with the same values as the constants of src/nes.inc; the source's own definitions are accepted over them. Emulator names the emulator to debug with (see Emulator).

Keys for other systems

A few Target keys only matter to other formats or machines. Three small configurations, each complete and built successfully with a one-unit main.asm that has no .org. A BBC Micro file with its code header:

    "RunAddress": "$1900",

    "System": "c128",
    "Hardware": {
      "Model": "c128",

{

Target

Class TargetConf. TargetResolver.Resolve starts from the catalog entry named by System (or by -t) and replaces each field the section sets; -cpu and -format are applied last. “Number” below means a string read by NumericLiteral: "$C000", "0xC000" and "49152" are the same value. The process is described on Targets.

Target.Ines

Class InesConf, applied by TargetResolver.ApplyInes and written by InesFormat. The defaults below are those of the nes family; a target that is not a NES but uses "Format": "ines" starts from the ResolvedTarget defaults instead, which differ only by 0 CHR banks. When the payload already starts with NES\x1A, as in the committed example_star_catcher whose header is assembled by src/header.asm, it is written unchanged and this whole section is ignored.

FieldTypeDefaultDescription
PrgBanksinteger1Number of 16 KB PRG banks, header byte 4. Zero or negative counts as 1.
ChrBanksinteger1 (NES systems)Number of 8 KB CHR banks, header byte 5. Negative counts as 0. The payload must fit in PRG + CHR (Payload is larger than iNES PRG+CHR size.); a shorter one is padded with zeros.
Mapperinteger0Mapper number: low nibble in the high nibble of byte 6, high nibble in byte 7. Only 0–255 can be expressed.
Mirroringstringverticalvertical or v sets bit $01 of byte 6; four, 4 or fourscreen sets $08; any other value (horizontal) sets neither.
BatterybooleanfalseSets bit $02 of byte 6 (battery-backed PRG RAM). Not optional like the others: whenever the Ines section is present, an absent Battery means false.

Target.Hardware

Class HardwareConf. Each key that is set replaces the preset's value (lower-cased), then HardwareRules.Reject refuses combinations the machine cannot have and the run stops with the reason, for example unknown video standard 'secam'. Use pal or ntsc. (Parameter 'config'). See Hardware variants.

The section is validated and stored, not applied: the hardware symbol table is the one the catalog built for the named System. Choosing "VideoChip": "vic" on a cbm2-80 does not define VIC; pick the catalog id that preselects the variant instead. The only other effect is in the prg format: a target with Hardware and no address gets an error instead of a guessed $0801.

VideoChipstringthe system'svic, vdc, ted or crtc. Refused: any chip on pet2001 / pet2001n; vdc outside c128, c128d, cbm2; ted outside plus4, c16; crtc outside cbm2.

The committed example

example_star_catcher/config.json as committed in the repository has no Target section, so the target is raw and the format bin: the image is written exactly as concatenated, and the iNES header is assembled from source:

{
	"Input": [
		{
			"FileName": "src/header.asm",
			"Dependencies": []
		},
		{
			"FileName": "src/game.asm",
			"Dependencies": []
		},
		{
			"FileName": "src/vectors.asm",
			"Dependencies": ["src/game.asm"]
		}
	],
	"Output": {
		"ObjectFile": "star_catcher.nes",
		"Files": [
			{
				"FileName": "src/header.o",
				"Size": "$10"
			},
			{
				"FileName": "src/game.o",
				"Size": "$3FFA"
			},
			{
				"FileName": "src/vectors.o"
			},
			{
				"FileName": "chr/tiles.chr"
			},
			{
				"FileName": "chr/floor.chr"
			}
		]
	},
	"Emulator": {
		"Name": "mesen2",
		"Path": "C:\\Emulators\\Mesen2\\Mesen.exe"
	}
}

header.asm emits the whole 16-byte header from .org $0000 ("NES", $1A, one PRG bank, one CHR bank, flags $00 and $00 (horizontal mirroring), then .dsb 8 zeros), so "Size": "$10" adds no padding: it only makes the build fail if the header ever grows. game.asm starts at .org $C000; its 5,336 bytes (the code, the data and the two 1,024-byte screens of gfx/) are padded to $3FFA, so that vectors.asm, at .org $FFFA, lands on the last six bytes of the 16 KB PRG bank. vectors.asm writes the addresses of NMI, RESET and IRQ, which game.asm defines, hence its dependency. chr/tiles.chr, drawn in the Graphics Designer, is 8 KB of tiles taken as they are. The image is 16 + 16,384 + 8,192 = 24,592 bytes. Emulator is for debugging only: Mesen2 at an example path, to point at your own (or override with the winasm65.emulatorPath setting in VS Code). The Example game page explains the same file from the game's side.

How units are resolved

The name of the section, “dependencies”, suggests a dependency graph sorted before the build. There is none. MultiSegmentOrchestrator.AssembleSegments works in two phases, both in the order the Input array lists the units, and Dependencies only says which symbol files a unit is allowed to read in the second phase.

Consequences

  • The order of Input does not decide whether names resolve. Every unit is assembled before any is resolved, so a unit may come before the unit it depends on, and two units may depend on each other (the README's own example has a cycle).
  • Every unit whose names you use must be listed. A name found in no declared dependency fails the build, reported at line 0 of the unit: Line 0 - File main.asm - Type Undefined symbol. A dependency whose .symb is missing (because it defined no global name) fails with Dependency symbol file doesn't exist.
  • Dependencies are not transitive, and a .symb is written once. It holds the names its unit could define on its own in phase 1. A constant that one unit computes from another unit's label (ALIAS = target + 1) is pending in phase 1, so it never reaches that unit's .symb, and a third unit cannot use it.
  • A placeholder keeps the width it was given. An operand that is unknown in phase 1 is emitted with a two-byte placeholder, before its value can be compared with $FF, so a reference to another unit's zero-page name keeps the absolute (three-byte) form of the instruction.
  • The address comes from .org. Each unit is placed by its own .org (or, without one, at the target's load address). Nothing in the project moves a unit; the Output order only has to agree with the addresses.

The side files

The only channel between units is the disk. The naming rule lives in SideFiles so that the writer (AssemblerEngine.ExportSymbolFiles) and the reader (the orchestrator) cannot disagree: the base name is the source path with its extension removed (Path.ChangeExtension(path, null)), and SideFiles.Locate puts the file beside the source unless a side-file directory was given, in which case it creates that directory and puts the file there under its own name.

FileType in JSONContent
.symbDictionary<string, long>Global names and their values, without generated names (local and anonymous labels). Written only when non-empty.
.UnsolvedDictionary<string, UnresolvedSymbol>Names whose value depends on a name still unknown, with a count of what is missing.
.UnsolvedExprDictionary<ushort, UnresolvedExpr>Placeholders in the object file, keyed by their position relative to the unit's origin, with the expression to evaluate.

Every unit also starts with the same predefined names: the target's hardware symbols (when DefineHardwareSymbols is on) and the region symbols of the memory map. They are known everywhere without a dependency. Since they sit in the unit's global table, they are also written to its .symb: with the complete example above, even src/vectors.asm, which defines nothing, leaves a vectors.symb holding PPUCTRL, ZEROPAGE_START and the rest.

MultiSegmentOrchestrator

The class that runs the Input stage. It does not assemble by itself: it is given a factory, Func<IAssembler>, and calls it once per unit in phase 1 and once more per unit resolved in phase 2.

MemberRole
MultiSegmentOrchestrator(Func<IAssembler>)Side files beside their sources (the command line).
MultiSegmentOrchestrator(Func<IAssembler>, string sideFileDirectory)Side files in a directory of the caller's choosing. It must be the same directory the assemblers were told to write to (AssemblerOptions.SideFileDirectory).

ResolveSegment (private)Phase 2 for one unit, as in the diagram above.
GetObjectFile (private)OutputFile, or the source path with .o.

The factory the caller passes sets ReportUndefinedSymbols = false. In single-file mode an unknown name is an error at the end of the file, because no other file can define it; in a project it is the normal case, and the orchestrator asks the question itself once the dependencies are loaded. The factory also carries the CPU, the predefined symbols, the listing switch and the default origin from the resolved target, so every unit is assembled for the same machine.

Combining files into an image

BinaryCombiner implements IBinaryCombiner, which has two methods:

MethodDoesUsed by
Concatenate(CombineConf, out byte[] payload)Builds the image in memory.the command line when the format is not bin; ProjectSession always
Combine(CombineConf)Calls Concatenate, creates the output directory if needed, and writes ObjectFile.the command line when the format is bin

For each entry of Files, in order, it reads the whole file and, if a Size is given, grows it to that size with zero bytes; then it appends it to the image. That is all: no alignment, no fill value, no overlap check.

The Size field

  • It is read as hexadecimal whether or not it starts with $: the code trims a leading $ and parses with NumberStyles.HexNumber. "100" means 256 bytes, not 100. Write the $ to make that visible.
  • A file larger than its Size, or a Size that does not parse, stops the build: Invalid target size for: main.o. The combiner never truncates.
  • The padding byte is always $00.
  • Without Size, the file takes exactly its own length.

Other failures: a missing file (Input file doesn't exist: …), and a missing ObjectFile (An output object file is required.).

Why the sizes matter

Each object file holds only the bytes its unit emitted, from its first .org onwards; the gaps between units do not exist on disk. Size recreates them. In the star_catcher.nes image, header.o is the 16-byte header; game.o holds 10,537 bytes of code and data from $C000 to $E928 and is padded to $3FFA, so vectors.o starts at the file offset that maps to $FFFA:

After combining: the format

The command line decides by format name. If it is bin (or empty), Combine writes the concatenation as it is. Otherwise Concatenate builds it in memory and ExecutablePublisher.Publish writes it in the target's format, so a project with "Target": { "System": "c64" } becomes a PRG. The iNES format, for one, recognises a payload that already starts with NES\x1A and writes it unchanged, so the committed example_star_catcher, whose header is assembled from source, gives the same star_catcher.nes with -t nes. In a project build the format does not see the units' .org: formats that write an address take it from RunAddress or LoadAddress (see Target). See Formats.

MemoryMap: declared regions

A Target section may declare named regions of the address space. They are declarative: a region places no byte and replaces no .org, and the output is byte-for-byte the same with or without them. What they add is checking, and symbols.

The regions of the complete example, for example_star_catcher:

"Regions": [
  { "Name": "ZEROPAGE", "Address": "$0000", "Size": "$100",  "Type": "bss" },
  { "Name": "OAM",      "Address": "$0200", "Size": "$100",  "Type": "bss" },
  { "Name": "RAMCODE",  "Address": "$0300", "Size": "$80",   "Type": "rw", "Load": "$E000" },
  { "Name": "PRG",      "Address": "$C000", "Size": "$3FFA", "Bank": 0, "Type": "ro" },
  { "Name": "VECTORS",  "Address": "$FFFA", "Size": "6",     "Type": "ro" }
]

The fields, their types and defaults are in Target.Regions[]. Unlike Output.Files[].Size, these addresses and sizes go through NumericLiteral, the assembler's own number parser, so "$C000" and "49152" are the same value.

What the map checks

  • At load (MemoryMap.TryBuild): a missing or unreadable Address, an unknown Type, a duplicate name, a region past $FFFF, and two sized regions that overlap. Each is a diagnostic, reported before any source is read.
  • Each .org (ValidateOrigin): an origin outside every region is an error that names the region it probably belongs to (the last one starting at or below the address) and lists all of them; an origin inside a bss region is an error, since that space produces no file bytes.
  • Each .res (ValidateReservation): a reservation that starts in a sized bss region and runs past its end is an error that says how many bytes fall outside. Reservations in ro and rw regions are not checked; a reservation past $FFFF always is.
Line 79  - File src/game.asm - Type $C000 lands outside every declared region. Expected region: RAMCODE $0300-$037F (rw). Declared regions: ZEROPAGE $0000-$00FF (bss), OAM $0200-$02FF (bss), RAMCODE $0300-$037F (rw), VECTORS $FFFA-$FFFF (ro).

That is the example above with the PRG region removed: the .org $C000 on line 79 of game.asm falls in no region, and the expected one is the last region that starts below it. Shrink ZEROPAGE to "Size": "$20" instead and the game's variables no longer fit: Line 72 - File src/game.asm - Type Reservation of 6 byte(s) at $001B overflows region 'ZEROPAGE', which ends at $001F. 1 byte(s) fall outside every declared region. (line 72 is obj_x .res MAX_OBJECTS).

A write that runs past the end of a region (as opposed to a .res) is not checked.

Region symbols

BuildPredefinedSymbols gives each region whose name is a valid identifier the symbols NAME_START, NAME_LOAD and NAME_RUN, plus NAME_END (last address) and NAME_SIZE when it has a size. They are merged over the hardware symbols, so a source can write:

        .memarea OAM_START
sprites .res OAM_SIZE

With the regions above this places sprites at $0200; asking for $101 bytes instead fails with Reservation of 257 byte(s) at $0200 overflows region 'OAM', which ends at $02FF. 1 byte(s) fall outside every declared region.

How the map reaches the assembler

The .org and .res directives are dispatched deep inside AssemblerEngine, so the map is not passed to them as a parameter. The build installs it with using (MemoryMapScope.Activate(map)) for the duration of the assembly, and the directives read MemoryMapScope.Current, a [ThreadStatic] field. A configuration without Regions installs null, which checks nothing.

ProjectSession: the build as a library call

The command line resolves every path against the process's current directory and writes everything to disk. That is fine in a terminal and wrong for an editor, whose current directory has nothing to do with the project. WinASM65.Projects.ProjectSession wraps the same pieces (TargetResolver, MemoryMap, MultiSegmentOrchestrator, BinaryCombiner, ExecutablePublisher) behind an explicit base directory, and returns the image and per-unit results in memory.

Opening a session

  • ProjectSession.Open(string configurationPath) reads the file; the base directory is the file's directory.
  • ProjectSession.Open(ConfigFile, string baseDirectory) takes a configuration already in memory. The language server uses it with an empty ConfigFile for a source that belongs to no project.
  • ProjectSession.Create(…) takes every collaborator (IConfigurationReader, IAssemblerFactory, IBinaryCombiner, IExecutablePublisher), for tests.

Every name of the configuration (sources, dependencies, output files, the image) is made absolute against BaseDirectory before the orchestrator sees it. SourceFiles lists the units, absolute, in declaration order.

Build options

Build(ProjectBuildOptions). With every option at its default the bytes are those of WinASM65 -c config.json.

OptionDefaultEffect
EnableListingfalseWrites a .lst per unit, as -l.
SideFileDirectorynull (beside the sources)Where .symb, .Unsolved and .UnsolvedExpr go. Object files still follow OutputFile or their source.
System, Cpu, FormatnullThe same overrides as -t, -cpu, -format.
WriteImagefalseWrites the image through ExecutablePublisher. Off, the image only exists in ProjectBuildResult.Image.
ImagePathnullWhere to write it; default Output.ObjectFile, or out.bin without one.
CaptureListingfalseKeeps each unit's listing rows and origins in memory (an InMemoryListingService) instead of writing .lst files, and computes Placements.

What a build returns

Member of ProjectBuildResultContent
Success, DiagnosticsWhether an image was produced, and every message of the build.
ImageThe concatenated payload. Empty on failure.
ImagePathWhere it was written, when WriteImage was set.
UnitsOne ProjectUnitResult per input: source and object paths, dependencies, the symbol table the unit's assembler ended with, and (when captured) its listing rows, its EmitterOrigins and its emitted length.
PlacementsWhen captured: one ImagePlacement per Output file, with its offset and length in the image, padding included, computed by the same rule as the combiner.

Units, origins and placements together are what lets a debugger turn a program counter into a file offset, a unit and a source line: see the debug adapter.

Listing one file against the project

After a successful build the session keeps ProjectSymbols, the union of every unit's names (the first unit to define a name wins). ListSourceFile(path) and ListSourceText(text, name) assemble one source in memory with those names, the target's CPU, load address and hardware symbols predefined. That is how an editor shows the listing of, and the errors in, one file of a multi-file project without reporting every name another file defines as undefined. A name defined by the file itself still wins over a predefined one, and a name no unit defines is still reported. Before the first build, ProjectSymbols is empty and the listing is that of the file alone.
