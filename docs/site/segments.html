Projects and segments

A config.json describes a program made of several sources: the units to assemble and which names each may take from the others, the files to put end to end into the final image, and optionally the target and the emulator. This page explains the file, the two-phase build behind it, and the classes that run it.

The build at a glance

A project build has two stages that know nothing about each other. The Input stage assembles each unit into its own object file, already placed at its real address by its own .org; names cross from one unit to another through small JSON side files. The Output stage then concatenates files, object files and plain binaries alike, padding each one to a declared size, and hands the result to the target's format.

The command line runs it as WinASM65 -c config.json, optionally with -l for listings and -t, -cpu, -format to override the target. The editor tools run the same build through ProjectSession.

The configuration file

JsonConfigurationReader deserializes the file with Newtonsoft.Json into a ConfigFile, which has three properties. Keys the classes do not declare are ignored, which is how the Emulator section can sit in the same file.

The two examples

As committed in the repository. example_nes_game assembles its iNES header from source:

{
	"Input": [
				{
					"FileName": "engine/headers.asm",
					"Dependencies": []
				},
				{
					"FileName": "engine/background.asm",
					"Dependencies": []
				},
				{
					"FileName": "engine/vectors.asm",
					"Dependencies": ["engine/background.asm"]
				}
			],
	"Output": {

				"ObjectFile": "generated_Nes_Rom/game.nes",
				"Files":
				[
					{
						"FileName": "engine/headers.o",
						"Size": "$10"
					},
					{
						"FileName": "engine/background.o",
						"Size": "$3FFA"
					},
					{
						"FileName": "engine/vectors.o"
					},
					{
						"FileName": "chr/mario.chr"
					}
				]
			}
}

headers.asm emits the 16 header bytes ("NES", $1A, then the bank counts) from .org $0000; background.asm starts at .org $C000 and is padded to $3FFA bytes, so that vectors.asm, at .org $FFFA, lands on the last six bytes of the 16 KB PRG bank. vectors.asm writes the addresses of NMI and RESET, which background.asm defines, hence its dependency.

example_bomberman-nes takes its header from a binary file and splits the code into two banks:

{
	"Input": [
				{
					"FileName": "BMAN_BANK1.NAS",
					"Dependencies": []
				},
				{
					"FileName": "BMAN_BANK2.NAS",
					"Dependencies": ["BMAN_BANK1.NAS"]
				},
				{
					"FileName": "vectors.NAS",
					"Dependencies": ["BMAN_BANK1.NAS","BMAN_BANK2.NAS"]
				}
			],
	"Output": {

				"ObjectFile": "bomber.nes",
				"Files":
				[
					{
						"FileName": "NES_Header.bin",
						"Size": "$10"
					},
					{
						"FileName": "BMAN_BANK1.o",
						"Size": "$3000"
					},
					{
						"FileName": "BMAN_BANK2.o",
						"Size": "$0FFA"
					},
					{
						"FileName": "vectors.o"
					},
					{
						"FileName": "bomber.chr"
					}
				]
			}
}

BMAN_BANK1.NAS starts at $C000 and fills $3000 bytes, BMAN_BANK2.NAS starts at $F000 and fills $0FFA, and vectors.NAS writes NMI, RESET and IRQ at $FFFA. The image is 16 + 16,384 + 8,192 = 24,592 bytes. Neither example has a Target section, so the format is bin and the image is written exactly as concatenated: the header is already in it.

The Emulator section

Neither committed example has one; a project adds it to say which emulator the tools start:

"Emulator": {
	"Path": "C:\\Tools\\Mesen2\\Mesen.exe"
}

Only Path is read, by EmulatorLauncher.FromProjectConfiguration in the monitor and by DebugEnvironment.ConfiguredEmulator in the debug adapter. A relative path is resolved against the directory of config.json. The monitor starts that program with the ROM (Output.ObjectFile, also resolved against the configuration directory) as its only, quoted argument. An Arguments key, as found in some local configurations, is not read by either: the launcher passes null as its argument template on purpose.

How units are resolved

The name of the section, “dependencies”, suggests a dependency graph sorted before the build. There is none. MultiSegmentOrchestrator.AssembleSegments works in two phases, both in the order the Input array lists the units, and Dependencies only says which symbol files a unit is allowed to read in the second phase.

Consequences

  • The order of Input does not decide whether names resolve. Every unit is assembled before any is resolved, so a unit may come before the unit it depends on, and two units may depend on each other (the README's own example has a cycle).
  • Every unit whose names you use must be listed. A name found in no declared dependency fails the build, reported at line 0 of the unit: Line 0 - File main.asm - Type Undefined symbol. A dependency whose .symb is missing (because it defined no global name) fails with Dependency symbol file doesn't exist.
  • Dependencies are not transitive, and a .symb is written once. It holds the names its unit could define on its own in phase 1. A constant that one unit computes from another unit's label (ALIAS = target + 1) is pending in phase 1, so it never reaches that unit's .symb, and a third unit cannot use it.
  • A placeholder keeps the width it was given. An operand that is unknown in phase 1 is emitted with a two-byte placeholder, before its value can be compared with $FF, so a reference to another unit's zero-page name keeps the absolute (three-byte) form of the instruction.
  • The address comes from .org. Each unit is placed by its own .org (or, without one, at the target's load address). Nothing in the project moves a unit; the Output order only has to agree with the addresses.

The side files

The only channel between units is the disk. The naming rule lives in SideFiles so that the writer (AssemblerEngine.ExportSymbolFiles) and the reader (the orchestrator) cannot disagree: the base name is the source path with its extension removed (Path.ChangeExtension(path, null)), and SideFiles.Locate puts the file beside the source unless a side-file directory was given, in which case it creates that directory and puts the file there under its own name.

FileType in JSONContent
.symbDictionary<string, long>Global names and their values, without generated names (local and anonymous labels). Written only when non-empty.
.UnsolvedDictionary<string, UnresolvedSymbol>Names whose value depends on a name still unknown, with a count of what is missing.
.UnsolvedExprDictionary<ushort, UnresolvedExpr>Placeholders in the object file, keyed by their position relative to the unit's origin, with the expression to evaluate.

Every unit also starts with the same predefined names: the target's hardware symbols (when DefineHardwareSymbols is on) and the region symbols of the memory map. They are not in any .symb but they are known everywhere.

MultiSegmentOrchestrator

The class that runs the Input stage. It does not assemble by itself: it is given a factory, Func<IAssembler>, and calls it once per unit in phase 1 and once more per unit resolved in phase 2.

MemberRole
MultiSegmentOrchestrator(Func<IAssembler>)Side files beside their sources (the command line).
MultiSegmentOrchestrator(Func<IAssembler>, string sideFileDirectory)Side files in a directory of the caller's choosing. It must be the same directory the assemblers were told to write to (AssemblerOptions.SideFileDirectory).
AssembleSegments(IReadOnlyList<Segment>)Runs both phases and returns a MultiSegmentResult (an OperationResult: success and diagnostics).
ResolveSegment (private)Phase 2 for one unit, as in the diagram above.
GetObjectFile (private)OutputFile, or the source path with .o.

The factory the caller passes sets ReportUndefinedSymbols = false. In single-file mode an unknown name is an error at the end of the file, because no other file can define it; in a project it is the normal case, and the orchestrator asks the question itself once the dependencies are loaded. The factory also carries the CPU, the predefined symbols, the listing switch and the default origin from the resolved target, so every unit is assembled for the same machine.

Combining files into an image

BinaryCombiner implements IBinaryCombiner, which has two methods:

MethodDoesUsed by
Concatenate(CombineConf, out byte[] payload)Builds the image in memory.the command line when the format is not bin; ProjectSession always
Combine(CombineConf)Calls Concatenate, creates the output directory if needed, and writes ObjectFile.the command line when the format is bin

For each entry of Files, in order, it reads the whole file and, if a Size is given, grows it to that size with zero bytes; then it appends it to the image. That is all: no alignment, no fill value, no overlap check.

The Size field

  • It is read as hexadecimal whether or not it starts with $: the code trims a leading $ and parses with NumberStyles.HexNumber. "100" means 256 bytes, not 100. Write the $ to make that visible.
  • A file larger than its Size, or a Size that does not parse, stops the build: Invalid target size for: main.o. The combiner never truncates.
  • The padding byte is always $00.
  • Without Size, the file takes exactly its own length.

Other failures: a missing file (Input file doesn't exist: …), and a missing ObjectFile (An output object file is required.).

Why the sizes matter

Each object file holds only the bytes its unit emitted, from its first .org onwards; the gaps between units do not exist on disk. Size recreates them. In the Bomberman image, BMAN_BANK1.o covers $C000–$EFFF once padded to $3000, so BMAN_BANK2.o starts at the file offset that maps to $F000:

After combining: the format

The command line decides by format name. If it is bin (or empty), Combine writes the concatenation as it is. Otherwise Concatenate builds it in memory and ExecutablePublisher.Publish writes it in the target's format, so a project with "Target": { "System": "c64" } becomes a PRG. The iNES format, for one, recognises a payload that already starts with NES\x1A and writes it unchanged, so the Bomberman layout above also works with -t nes. See Formats.

MemoryMap: declared regions

A Target section may declare named regions of the address space. They are declarative: a region places no byte and replaces no .org, and the output is byte-for-byte the same with or without them. What they add is checking, and symbols.

{
  "Target": {
    "System": "nes",
    "Regions": [
      { "Name": "PRG0",    "Address": "$C000", "Size": "$3000", "Bank": 0, "Type": "ro" },
      { "Name": "PRG1",    "Address": "$F000", "Size": "$0FFA", "Bank": 1, "Type": "ro" },
      { "Name": "VECTORS", "Address": "$FFFA", "Size": "$6",    "Type": "ro" },
      { "Name": "OAM",     "Address": "$0200", "Size": "$0100", "Type": "rw" },
      { "Name": "VARS",    "Address": "$0300", "Size": "$0180", "Type": "bss" }
    ]
  }
}
FieldRequiredMeaning
NamenoUsed in messages and to name the region's symbols. Default #index. Duplicates are refused.
AddressyesThe base, where code runs: what a .org is checked against.
SizenoBytes. Absent: the region runs to $FFFF. Must not pass the end of the address space.
BanknoBank number, informative; must not be negative.
Typenoro (default, also r), rw (also r/w) or bss.
LoadnoWhere the bytes are stored, when that differs from where they run.

Unlike Files[].Size, these addresses and sizes go through NumericLiteral, the assembler's own number parser, so "$C000" and "49152" are the same value.

What the map checks

  • At load (MemoryMap.TryBuild): a missing or unreadable Address, an unknown Type, a duplicate name, a region past $FFFF, and two sized regions that overlap. Each is a diagnostic, reported before any source is read.
  • Each .org (ValidateOrigin): an origin outside every region is an error that names the region it probably belongs to (the last one starting at or below the address) and lists all of them; an origin inside a bss region is an error, since that space produces no file bytes.
  • Each .res (ValidateReservation): a reservation that starts in a sized bss region and runs past its end is an error that says how many bytes fall outside. Reservations in ro and rw regions are not checked; a reservation past $FFFF always is.
Line 3 - File BMAN_BANK1.NAS - Type $C000 lands outside every declared region.
Expected region: PRG1 $F000-$FFF9 (ro). Declared regions: PRG1 $F000-$FFF9 (ro).

A write that runs past the end of a region (as opposed to a .res) is not checked.

Region symbols

BuildPredefinedSymbols gives each region whose name is a valid identifier the symbols NAME_START, NAME_LOAD and NAME_RUN, plus NAME_END (last address) and NAME_SIZE when it has a size. They are merged over the hardware symbols, so a source can write:

        .memarea VARS_START
vars    .res VARS_SIZE

How the map reaches the assembler

The .org and .res directives are dispatched deep inside AssemblerEngine, so the map is not passed to them as a parameter. The build installs it with using (MemoryMapScope.Activate(map)) for the duration of the assembly, and the directives read MemoryMapScope.Current, a [ThreadStatic] field. A configuration without Regions installs null, which checks nothing.

ProjectSession: the build as a library call

The command line resolves every path against the process's current directory and writes everything to disk. That is fine in a terminal and wrong for an editor, whose current directory has nothing to do with the project. WinASM65.Projects.ProjectSession wraps the same pieces (TargetResolver, MemoryMap, MultiSegmentOrchestrator, BinaryCombiner, ExecutablePublisher) behind an explicit base directory, and returns the image and per-unit results in memory.

Opening a session

  • ProjectSession.Open(string configurationPath) reads the file; the base directory is the file's directory.
  • ProjectSession.Open(ConfigFile, string baseDirectory) takes a configuration already in memory. The language server uses it with an empty ConfigFile for a source that belongs to no project.
  • ProjectSession.Create(…) takes every collaborator (IConfigurationReader, IAssemblerFactory, IBinaryCombiner, IExecutablePublisher), for tests.

Every name of the configuration (sources, dependencies, output files, the image) is made absolute against BaseDirectory before the orchestrator sees it. SourceFiles lists the units, absolute, in declaration order.

Build options

Build(ProjectBuildOptions). With every option at its default the bytes are those of WinASM65 -c config.json.

What a build returns

Member of ProjectBuildResultContent
Success, DiagnosticsWhether an image was produced, and every message of the build.
ImageThe concatenated payload. Empty on failure.
ImagePathWhere it was written, when WriteImage was set.

Units, origins and placements together are what lets a debugger turn a program counter into a file offset, a unit and a source line: see the debug adapter.

Listing one file against the project

After a successful build the session keeps ProjectSymbols, the union of every unit's names (the first unit to define a name wins). ListSourceFile(path) and ListSourceText(text, name) assemble one source in memory with those names, the target's CPU, load address and hardware symbols predefined. That is how an editor shows the listing of, and the errors in, one file of a multi-file project without reporting every name another file defines as undefined. A name defined by the file itself still wins over a predefined one, and a name no unit defines is still reported. Before the first build, ProjectSymbols is empty and the listing is that of the file alone.
