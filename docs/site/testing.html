Notable techniques

Golden SHA-256 hashes

Whole outputs are pinned by their SHA-256, so a parser change that alters a single byte fails a test:

WhatWhereHow
The Bomberman NES image (4E57F087…C810A244)ProjectSessionTests, ProjectBuildVerbTests, NesEmulatorTestsProjectSessionTests builds example_bomberman-nes through the library, compares it byte for byte with the image the original toolchain produced, then checks the hash. The comparison is Inconclusive when bomber.nes is absent.

Code that really runs

  • On the built-in 6502 core. TestCpu6502Tests checks the interpreter against known answers; ExecutionCoreTests and RuntimeStubTests run assembled code on it.
  • On Mesen. NesEmulatorTests links a shared routine at two addresses, wraps each image in an iNES ROM, runs it in Mesen's test-runner mode, and reads back marker bytes the routine writes to RAM. Byte $11 must be $80 for the unshifted image and $90 for the shifted one, which proves the relocations were rewritten.

The monitor without an emulator

  • A real socket. ProtocolServer serves the bridge protocol on top of any IMemoryBackend. BridgeMemoryBackendTests, ProtocolTests, BreakpointSetTests, RelocatableUnitTests, AdapterCapabilityTests and MonitorProgramTests put the real BridgeMemoryBackend and ProtocolClient against it over TCP, including the 256-byte chunking and the rule that an ERR reaches the user with its reason intact.
  • The real executable. MonitorProgramTests starts WinASM65.Monitor, writes commands to its standard input and checks what it prints: argument parsing, the handshake, the prompt, and that a typo does not end the process.
  • A headless terminal. The shell tests build the real ShellWindow on SharpConsoleUI's HeadlessConsoleDriver; the lifecycle tests go through ShellRunner.Run's overload that stops after a given number of frames. ShellChromeRenderTests reads the screen buffer the driver was left holding. ShellLifecycleTests also starts a real child process to check that no emulator is left orphaned.
  • Pure functions where a UI would be. ShellLayout, ShellStatus, ShellCapabilities, EditorCommands and StateCommands contain no UI types, so the tests assert exact widths, status lines, refusal wording and the command line each key sends.
  • The real workload. NesSourceReachabilityTests opens the Bomberman sources in the editor's listing. It found two real defects: .nas was not a recognised source extension, and a source that failed to assemble showed an empty pane with a misleading reason.

A fake debug machine for the DAP

DebugSessionTests runs the real DebugSession on its own thread with a FakeEnvironment: the real assembler, a FakeEmulator, and a FakeDebugMachine. The fake machine implements IMemoryBackend, ICpuStateSource, IExecutionEvents and IBreakpointRemoval over a 64 KiB array, records every call, and stops when the test says so. Its stops and resumes are raised on a separate thread, in order, as the bridge's receiver thread would raise them. The builds and the source map are real.

LSP tests

LanguageServerTests runs LanguageServer in-process on a thread, sends JSON-RPC messages through Dispatch, and collects what the server publishes into a queue. Each test writes its sources to a temporary directory, sends initialize with that directory as the root, and waits up to 10 s for the expected message, such as textDocument/publishDiagnostics for a given URI.

The grammar against the assembler

GrammarTests reads vscode-extension/syntaxes/winasm65.tmLanguage.json, takes the longest alternation in the relevant patterns, and compares it with what the assembler accepts: every mnemonic of every CPU in CpuFactory.All and every directive the engine dispatches, and nothing else. A new opcode or directive that the grammar does not colour fails the build.

The VS Code extension test

vscode-extension/src/test/ holds one integration test that runs inside a real VS Code. runTest.ts uses @vscode/test-electron to start VS Code with the extension under development, --disable-extensions and a temporary user-data directory, on example_nes_game. suite.ts then checks:

  • engine/background.asm opens with the language id winasm65;
  • the extension codewinbzn.winasm65 activates, and the commands winasm65.showListing, winasm65.hideListing and winasm65.showRam are registered;
  • after winasm65.showListing, the listing column draws more than 40 rows for the file within 30 s.
# PowerShell: clear the variables a VS Code terminal sets, keep VSCODE_EXECUTABLE
Get-ChildItem env: | Where-Object { $_.Name -match '^(VSCODE_|ELECTRON_)' -and $_.Name -ne 'VSCODE_EXECUTABLE' } |
  ForEach-Object { Remove-Item "env:$($_.Name)" }
cd vscode-extension
npm test        # tsc -p ./ && node out/test/runTest.js

Run it with VSCODE_* and ELECTRON_* unset. The VS Code instance the test starts inherits the environment of npm test. Started from a terminal inside VS Code (or from a tool running in one), the variables VS Code exports there interfere with the instance under test. tools/screenshots/vscode.mjs strips the same two prefixes before it launches VS Code. VSCODE_EXECUTABLE is the test's own option: it points at an installed VS Code instead of downloading one.

The tools folder

Scripts for what the unit tests cannot cover: a real Mesen2, and pictures of the real programs. Close any running Mesen2 first: it is a single-instance program and would take over the launch.

tools/dap-smoke.py

python tools/dap-smoke.py <adapter.exe|adapter.dll> <config.json> <source> <line>

Drives the debug adapter (<adapter> --dap, or dotnet <adapter.dll> --dap) over stdin/stdout exactly as VS Code would, against a real Mesen2. It prints PASS/FAIL for each step: initialize and launch; a verified breakpoint at <source>:<line>; a stop there with matching stack frame and PC; next moves to a later line; readMemory returns all 2 KiB of RAM; the custom winasm65.symbols request names RAM symbols; the debug console answers CPU; continue hits the breakpoint again; without breakpoints the machine keeps running; pause stops; disconnecting ends the emulator.

tools/mesen2-bridge-check.py

python tools/mesen2-bridge-check.py <Mesen.exe> <rom.nes> <exec-address-hex>

Starts Mesen2 with bridge_mesen2.lua on port 45699 and speaks the bridge protocol directly, without any .NET code. The address must be an instruction the ROM executes repeatedly (an NMI handler is ideal). It checks: PING and STATUS; a breakpoint stops before its instruction (PUSH STOPPED reason=breakpoint pc=<address>); STEP stops one instruction later; BREAK REMOVE and BREAK CLEAR really remove; PAUSE stops with reason=pause; every RESUME is followed by PUSH RESUMED.
