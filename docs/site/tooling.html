Tooling: DAP and LSP

WinASM65.Tooling is the editor side of WinASM65: one executable that runs as a Debug Adapter, a Language Server or a build front end. The VS Code extension starts it; any other editor that speaks DAP or LSP could too.

One program, three modes

Program.Main reads its first argument and picks a mode. Anything else prints a usage text on stderr and exits with code 2.

Solid arrows: calls into a library. Dashed: a runtime connection. The project references are the ones in WinASM65.Tooling.csproj: WinASM65 and WinASM65.Monitor.Core.

No duplicated logic

The build, the listings, the source map and the bridge protocol are the ones the terminal monitor uses. A fix in either place reaches both front ends.

stdout belongs to the protocol

In --dap and --lsp, TakeProtocolStreams opens the raw standard streams, then points Console.Out at stderr, so nothing a library prints can land inside a message.

No protocol library

DAP and LSP share one framing, and the requests answered are few, so both are written by hand on System.Text.Json. No extra NuGet package.

One thread does the work

In both protocol modes a background reader thread only queues messages; a single loop (Run) handles them in order from a BlockingCollection<Action>.

Message framing

Rpc/MessageStream.cs implements the framing both protocols use: a Content-Length header, a blank line (both lines end in CR LF), then exactly that many bytes of UTF-8 JSON.

Content-Length: 61

{"seq":1,"type":"request","command":"threads","arguments":{}}
  • Reading goes byte by byte up to the body, never through a buffered reader: a reader that buffered past the header would swallow the start of the next message. Header names are compared case-insensitively; other headers are ignored; a stray blank line between messages is skipped.
  • Errors. A bad Content-Length or a body that is not a JSON object throws InvalidDataException. The reader thread catches it (with IOException and JsonException), writes it to stderr and ends the session as if the input had closed.
  • Writing is serialised by a lock, because the DAP session sends events and responses from more than one place. Each message is flushed at once.

Debug adapter

DebugSession is one debugging session of a 6502 machine. Every request and every event from the machine is handled on the session loop. The bridge reports stops on its receiver thread, which must never wait for a reply (it is the thread that delivers replies), so the Stopped and Resumed events are only queued with Post; a handler on the loop is then free to read registers or memory.

A launch and a breakpoint hit

The exchange when you press F5 on the Bomberman example with a breakpoint on line 30 of BMAN_BANK1.NAS, the first instruction of NMI at $C01A:

  1. Build. launch builds the project with the image written. A failed build fails the request (“the build failed; see the debug console”); each diagnostic has been printed to the debug console as file:line: message. On success the listings become the SourceMap, and the console says how many units and mapped lines it has.
  2. Start. The emulator is the emulatorPath argument, else Emulator.Path of config.json; with neither, the launch fails and says where to set one.
  3. Connect. The adapter retries a one-second connection every 200 ms until the timeout, and gives up early if the emulator process has exited. An early exit gets its own message: Mesen2 runs as a single instance, so a second launch is handed to the window already open and the new process quits.
  4. Check. The bridge must report execution state (IExecutionEvents.ReportsExecutionState) and the CPU state (ICpuStateSource). Otherwise the launch is refused with “… cannot be debugged: its bridge does not report when the machine stops”: that is the case of the MesenCE bridge.
  5. Hold. The machine is paused until configurationDone, so the breakpoints VS Code is about to send are in place before the program runs one frame.
  6. Run. configurationDone resets the machine, so the program starts from its reset vector. With stopOnEntry, a temporary breakpoint is first planted at the address read from $FFFC, and the stop is reported with the reason entry. After an attach nothing is reset: the machine is paused only with stopOnAttach, and a machine that is already stopped is reported as stopped.

Requests

initialize announces supportsConfigurationDoneRequest, supportsReadMemoryRequest, supportsWriteMemoryRequest, supportsEvaluateForHovers and supportsTerminateRequest; stepping granularity, restart and setVariable are declared unsupported. Every request the dispatcher knows:

A PC with no source gets a subtle frame without a source. The frame carries instructionPointerReference.

disconnectClears the breakpoints and closes the connection. The emulator is killed when terminateDebuggee says so, which defaults to “the adapter launched it”; an attached machine is resumed instead.

Any other command fails with “unsupported request”. In particular there is no disassemble, setVariable, restart, data breakpoints or conditional breakpoints. A MonitorException or an IOException from the bridge fails the request with its message rather than ending the session.

Breakpoints

  • Line to address. SourceMap.TryNearestEmittingLine moves a breakpoint set on a label, a comment or a blank line to the first line that emits code, at most 5 lines further down. SourceMap.AtLine then gives every address that line emitted (a macro or a repeat can emit several). With no build yet the message is “the project is not built yet”; with no code nearby, “no code at or after this line”.
  • Reference counts. The adapter counts user breakpoints per address and keeps a separate set of temporary ones (step over, step out, entry). An address is set on the bridge (BREAK SET exec) when the first of them wants it, and removed (BREAK REMOVE) when the last one lets it go. Without single removal, the bridge is cleared and the remaining addresses are set again.
  • Banks. Two banks can be assembled at the same CPU address. When a line's address is shared, the breakpoint is verified with the message “this address is shared with another bank; only this bank stops”. On a stop, the PRG offset the bridge reports is compared with the one the source map computed for the line: a stop in the other bank resumes the machine without telling VS Code.

Interpreting a stop

  1. Before configurationDone a stop is only remembered: it is the launch pause.
  2. A stop on a temporary breakpoint that is not also a user breakpoint is reported as step (or entry), and the temporaries are removed.
  3. A stop on a user breakpoint's address in another bank is resumed silently.
  4. Otherwise the reason is breakpoint (with hitBreakpointIds), step or pause, with allThreadsStopped.

A RESUMED the adapter did not cause (a click in Mesen2's own window) becomes a continued event. A one-second watchdog ends the session with terminated when the bridge connection drops, and the emulator's Exited event does the same when Mesen2 is closed.

Language server

LanguageServer gives diagnostics as you type and a hover that shows what a line assembled to. It runs on one worker thread; the reader only queues. initialize answers these capabilities and the server name winasm65:

Capability or methodImplementation
textDocumentSyncOpen/close, full sync (change: 1: the whole text on each change), save without text.
textDocument/didOpen, didSaveBuilds the whole project that governs the file and publishes its diagnostics.
textDocument/didChangeKeeps the new text; 250 ms after the last change, lists the unsaved text.
textDocument/didCloseForgets the text; a file outside any project has its diagnostics cleared.

An unknown request is answered with JSON-RPC error -32601 (method not found); an unknown notification is ignored. There is no completion, go to definition, references, symbols or formatting. Errors inside a handler are sent as window/logMessage.

Which project governs a file

  1. The config.json that lists the file as an input (ProjectConfigLocator, searched from the workspace root). The file is then a unit.
  2. Otherwise the nearest config.json above the file, up to 8 levels. The file is then treated as an include: only a build knows the context it is read in.
  3. Otherwise none: the file is assembled on its own, with an empty configuration.

Each project is opened once (ProjectSession.Open) and kept. Its builds put the .symb, .Unsolved and .UnsolvedExpr side files in a scratch directory under the system temp folder, one per project, deleted when the server stops.

Hover cards

HoverCard lays the markdown out like a JSDoc card: the code in a block, a title and one sentence, then @tag lines, then a reference table. The line is listed from the unsaved text, with the CPU of the project's target (the NMOS 6502 when none resolves).

On a mnemonic, or an instruction line

The source line; LDA — Load A and its summary (InstructionDescriptions); @mode with the syntax of the assembled form; @cycles; @bytes with the bytes and address; @flags. Then every form of the mnemonic: syntax, mode, opcode, bytes, cycles (+p page cross, +b branch taken, +d decimal mode), the assembled form marked ◀.

On a name

NAME = $60, @value in hex and decimal. If the line it is read on assembled to something, that line follows with its @cycles and @bytes. The value comes from the project's symbols, or from a label, constant or .res of the file itself.

The assembled form is found by matching the row's first byte and length against InstructionDocs and checking that the mnemonic is written on the line, so a .byte $A9, $01 row is not mistaken for LDA #$01. Screenshots are on the VS Code page.

The winasm65/listing request

→ { "textDocument": { "uri": "file:///c%3A/…/BMAN_BANK1.NAS" } }
← { "rows": [ { "line": 29, "address": 49178, "bytes": "48", "more": false }, … ] }
  • One row per source line that emitted bytes: the zero-based line, the address and bytes of its first emission, and more when the line emitted several times (a macro, a repeat).
  • A unit (or a file outside any project) is listed from its unsaved text, so the column follows the edit.
  • An include only exists inside a unit: its rows come from the last successful build, and are empty until there is one.

URIs

VS Code escapes the drive colon (file:///c%3A/x), which Uri.LocalPath would leave as /c:/x. PathOf unescapes the path and drops the leading slash by hand; UNC paths keep their host. Diagnostics for an open file are published under the exact URI VS Code used for it.

Known limits

  • One stack frame. The JSR chain is not reconstructed; the frame is named after the nearest label. stepOut assumes the top of the stack is the return address.
  • No disassembly view. disassemble is not implemented.
  • Mesen2 only. The MesenCE bridge does not report stops and is refused. Mesen2 runs as a single instance: close it before pressing F5.
  • Banks. A stop in a bank is told apart only when both the bridge and the source map know the PRG offset.
