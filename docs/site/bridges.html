Emulator bridges

How WinASM65 talks to an emulator, whatever the emulator and whatever the machine: a small script inside the emulator (the bridge) answers a line protocol on a TCP port, and an adapter knows how to start that emulator with it. This page is the contract a bridge implements and the way a project chooses its emulator.

The pieces

  • The bridge is a script the emulator runs (Lua for Mesen2). It is the only part that knows the emulator's API.
  • The adapter knows how to start that emulator with that script: command line, settings to prepare. A project can also describe a command line itself (the custom adapter).
  • The system definition (NesSystem, …) says what the machine has: its memory map, the memories behind its video chip, how a program starts. It is chosen from the project's Target.System, else from what the bridge reports, else from the image's header.

Choosing an emulator in config.json

"Emulator": {
    "Name": "mesen2",
    "Path": "C:\\Emulators\\Mesen2\\Mesen.exe",
    "Bridge": "bridges/my_bridge.lua",
    "Arguments": "{rom} {script}",
    "Port": 45678
}
KeyRequiredMeaning
PathyesThe emulator's executable. Relative to config.json.
NamenoThe adapter: mesen2, mesence, or any other name for a custom emulator. Without it, a Mesen.exe is taken for Mesen2 and anything else is custom.
BridgenoThe bridge script, replacing the adapter's own: a path (relative to config.json) or the file name of a bridge shipped with WinASM65.
Argumentscustom onlyThe command line of a custom emulator. {rom}, {script} and {port} are replaced; double quotes group words. Without it, the ROM alone is passed.
PortnoThe port the terminal monitor uses for an emulator it starts (the debug adapter picks a free one).

Key names are case-insensitive. The same section is read by the VS Code debugger, the terminal monitor and the MCP server; in VS Code the setting winasm65.emulatorPath and a launch configuration's emulatorPath/emulator override it.

Every bridge is also told its port in the environment variable MACHINE_PORT, because not every emulator can pass arguments to a script.

The line protocol

The debugger connects to the bridge on 127.0.0.1:<port> and sends one command per line. Every command gets exactly one answer line, starting with OK or ERR followed by a reason. Numbers are hexadecimal with $ unless said otherwise; byte strings are hexadecimal without separators.

Handshake: PING and HELLO

> PING
OK Mesen2 2.1.1
> HELLO
OK protocol=2 name=Mesen2 version=2.1.1 system=nes caps=memory,cpu,pause,resume,reset,step,break,watchread,watchwrite,state,status spaces=PPU,PAL,OAM,CHR

PING answers the emulator's name and version. HELLO is contract version 2: the bridge says what it is and what it can do, and the debugger believes it. A bridge that answers HELLO with an error is a version 1 bridge; its capabilities then come from the table of emulators WinASM65 was measured against (ExecutionCapabilities), and it has no memory spaces.

HELLO fieldMeaning
protocolContract version, 2 or more.
name, versionThe emulator, shown to the user and in refusals.
systemThe machine running, as a WinASM65 system id (nes, c64, …). Used when the project names none.
capsWhat works, comma-separated: memory (or read, write), cpu, pause, resume, reset, step, break, watchread, watchwrite, state. Unknown words are ignored. A command whose capability is missing is refused by the debugger with the bridge's name, before it is sent.
spacesMemories other than the CPU's that READ and WRITE accept as SPACE:address. Their names are the system definition's (NES: PPU, PAL, OAM, CHR).

Commands

CommandAnswerCapability
READ [space:]$addr nOK <hex>, n bytes (at most 4096). Without a space, the CPU's bus. Reads must not have side effects (no cleared flags).memory
WRITE [space:]$addr <hex>OK once the bytes read back as written; an error naming the address otherwise (read-only memory). At most 4096 bytes.memory
CPUOK pc=$C000 a=00 x=00 y=00 sp=FD ps=24 cycles=7 (cycles in decimal).cpu
STATUSOK running, or OK stopped reason=<breakpoint|step|pause> pc=$C06E prg=$0006E. prg is the offset in the program memory, or -.status
PAUSE, RESUME, STEP, RESETOK; the stop or the resumption is then pushed.pause, resume, step, reset
BREAK SET|REMOVE <exec|read|write> $addr, BREAK LIST, BREAK CLEAROK; LIST answers the breakpoints or none.break
ROM, ROM LOAD <path>The loaded image's description as key=value; replaces the image when the emulator can.—
STATE SAVE, STATE LOAD <hex>An opaque snapshot, at most 128 KB, and its restoration.state

Lines the bridge sends on its own

  • PUSH STOPPED reason=breakpoint pc=$C06E prg=$0006E when the machine stops (breakpoint, step, pause). A breakpoint stops before its instruction.
  • PUSH RESUMED when it runs again.
  • PUSH RAM $0010:42 $0011:00 … while running, the bytes written since the last push (at most 4096 per line).

Writing a bridge for another emulator

  1. Listen on the port in MACHINE_PORT and answer one line per command, without blocking the emulation for long: answer between frames, and in chunks (the debugger never asks for more than 256 bytes at once).
  2. Answer PING and HELLO; announce only the capabilities that really work, and the memory spaces with the names of the machine's system definition.
  3. Implement READ/WRITE, then CPU and STATUS; then the execution commands your emulator's scripting allows. A missing command must answer ERR with the reason, never a wrong OK.
  4. Describe the emulator in config.json with a Name, its Path, the Bridge and the Arguments that load the program and the script. No WinASM65 code changes; an adapter class is only needed for an emulator with something to prepare (as Mesen2's script sandbox settings).
  5. If the machine has no definition yet, it debugs as a generic 6502 (flat 64 KB, no other memory). Add a class to WinASM65.Systems to give it its memories and boot.

Checking a bridge

python tools/mesen2-bridge-check.py <Mesen.exe> <rom.nes> <address> runs the Mesen2 bridge against a real Mesen2 and checks every command: HELLO and the memory spaces, then a breakpoint that stops before its instruction, a step, removal, pause and resume. It is the model for checking another bridge.

PASS HELLO describes the bridge: OK protocol=2 name=Mesen2 version=2.1.1 system=nes caps=… spaces=PPU,PAL,OAM,CHR
PASS READ PAL reads the 32 palette bytes
PASS WRITE PAL changes a colour
PASS WRITE CHR changes a tile
PASS PPU:$3F00 is palette entry 0 through the PPU bus
PASS a breakpoint stops before its instruction: PUSH STOPPED reason=breakpoint pc=$C06E prg=$0006E
PASS STEP stops one instruction later: PUSH STOPPED reason=step pc=$C06F prg=$0006F

Contract version 2. Version 1 bridges (MesenCE) keep working with the capabilities measured for them.
