Targets and formats

A target says which machine a program is for: its CPU, where code goes by default, which hardware registers are predefined, and what file is written around the bytes. This page covers the catalog of systems, how a target is resolved, every output format, GEOS applications on D64 disks, and the BASIC tokenizer for the systems that do not run machine code at all.

Three families of target

The systems WinASM65 knows do not all want the same thing, and the code is organised around the difference:

FamilySystemsThe file isWritten by
Flat executableNES, Commodore machines, Apple II, Atari 8-bit and 2600, BBC Micro and its second processor, Electron, Oric, Lynx, Commander X166502 code at a fixed address, inside a container (iNES, PRG, XEX…)ExecutablePublisher and one IExecutableFormat per container

The prodos, dos32 and dos33 containers appear in two families: as executable formats they put machine code on a disk image as a binary file, and as BASIC containers they put an Applesoft program there.

How a target is resolved

Everything a build needs to know about its machine ends up in one object, ResolvedTarget. TargetResolver.Resolve(TargetConf config, string cliSystem, string cliCpu, string cliFormat) builds it from four sources, each overriding the previous one:

  1. Defaults. A new ResolvedTarget is raw, CPU 6502, format bin, no addresses, one PRG bank, vertical mirroring.
  2. Preset. The system id is -t if given, otherwise Target.System. SystemCatalog.TryGet normalises it (case, - and _ ignored) and returns a clone of the catalog entry, so that the following steps never modify the catalog itself. An unknown id throws Unknown system 'zx81'. Use -t list.
  3. Target section. Each field that is set replaces the preset's: Cpu, Format, LoadAddress, RunAddress, RomSize, DefineHardwareSymbols, Ines, Hardware, BbcFileType, Title, Author. Addresses go through the assembler's number parser, so "$0801" and "2049" are equal.
  4. -cpu, then -format, replace the CPU and the format. Command-line flags therefore always beat the file, and one config.json can be built for several systems. LoadAddress and RunAddress have no flag: a value in the file always applies.

The same resolver serves the command line, ProjectSession (whose System, Cpu and Format options play the role of the flags) and the link verb (which only passes -cpu and -format).

Hardware variants as options

Commodore machines and the NES come in variants: PAL or NTSC, two SID revisions, VIC-II or VDC or TED. Instead of one catalog entry with its own symbol table per combination, a machine is described by a HardwareOptions object with four fields, and HardwareProfile.Build(options) derives the symbol table: one table per family, then the differences applied.

OptionValuesWhat it changes
Modelc64, c64c, c128, c128d, vic20, plus4, c16, pet2001, pet2001n, cbm2, nesThe family table.
VideoStandardpal, ntscNo address on any Commodore machine. On the NES it adds FRAME_LINES, VISIBLE_LINES and IS_PAL; on TED machines, IS_PAL.
VideoChipvic, vdc, ted, crtcWhich chip answers at which address (CBM-II: CRTC or VIC-II at $D800; C128: VDC).
SoundChip6581, 8580, ted, vicA chip revision, recorded but moving no register.

The named variants of the catalog (c64-pal, c128-vdc, nes-pal…) only preselect options; -t list shows them as hw=…, the only trace of the variant in a build, since a PAL and an NTSC build of the same Commodore program give the same bytes.

A Target.Hardware section in config.json overrides the preset's options field by field. HardwareRules.Reject then refuses combinations the machine cannot have, and the resolver throws with the reason:

{ "Target": { "System": "c64", "Hardware": { "VideoChip": "vdc" } } }

the 8563 VDC exists on the C128 and the CBM-II, not on the c64. (Parameter 'config')

Other refusals: a video chip on a PET 2001 (its video is discrete logic), a SID on a Plus/4 or C16, a TED outside the Plus/4 and C16, a CRTC outside the CBM-II, an unknown video standard or sound chip.

In the current code the Hardware section is validated and stored on the target, but the symbol table is the one the catalog built for the named system: HardwareProfile.Build is only called by SystemCatalog. A cbm2-80 target with "VideoChip": "vic" is accepted, yet VIC stays undefined. To get another variant's symbols, choose the catalog id that preselects it.

Executable formats

A format is a class implementing IExecutableFormat:

public interface IExecutableFormat
{
    string Name { get; }
    OperationResult Write(string path, byte[] payload, ResolvedTarget target);
}

ExecutablePublisher registers one instance of each in a case-insensitive dictionary keyed by Name, and Publish(path, payload, target) looks up target.FormatName (empty means bin). An unknown name returns a diagnostic listing the accepted names. The formats write through ExecutableFile.WriteBytes / WriteText, which create the output directory if needed.

“Origin” is ResolvedTarget.OriginAddress, the address the code was really assembled at, so a .org in the source always wins over the target's default. The link verb, which has no source, sets LoadAddress to the linked image's origin instead.

Not in the table: w65. -format w65 is intercepted by CommandLineApplication before the publisher and writes a relocatable module with W65Format.Write (see Modules). And the D64 image is not a format either: only the geos verb writes one.

iNES header

The header is N E S $1A, the PRG bank count (at least 1), the CHR bank count, then two flag bytes. Byte 6 holds the low nibble of the mapper in its high nibble, $02 for a battery, and the mirroring: vertical or v sets $01, four, 4 or fourscreen sets $08, anything else (horizontal) sets neither. Byte 7 holds the high nibble of the mapper. All of it comes from the Ines section:

{
	"Target": {
		"System": "nes",
		"Ines": {
			"PrgBanks": 2,
			"ChrBanks": 1,
			"Mapper": 0,
			"Mirroring": "vertical",
			"Battery": false
		}
	}
}

The payload is copied as one block after the header, so it must already be laid out as the PRG banks followed by the CHR data, which is what a combined project image gives.

BBC code header

The BBC has no executable header with a length in it. The one self-describing format the machine accepts is the code header, which BbcFormat.BuildHeader writes:

+0   4C lo hi        JMP to the code, after the header
+3   EA EA EA        filler
+6   type            $60 (file, load address present) | CPU id (2 = 6502)
+7   offset          of the $00 that precedes the "(C)" marker
+8   title, $00      Target.Title, default "1.00"
     $00 "(C) author" $00     Target.Author, default "WinASM65"
     load address    4 bytes, low first
     the code

A payload that already starts with a JMP is taken as carrying its own entry: the three bytes of the JMP are removed and its target becomes the load address in the header, so the code is not shifted behind a second entry point.

Apple II disk images

ProDosImage.cs follows the ProDOS 8 Technical Reference: two reserved blocks, four directory blocks (the volume header is the first entry of block 2), a 32-block bitmap, then data; a file of one block or less is a seedling, a larger one a sapling with an index block; blocks are written with the interleave 0, 8, 1, 9, 2, 10, … in each group of sixteen. The load file inside starts with a header record (kind, version, minimum version, entry point as an offset in the file), then a record per segment (number, length, load address, name) followed by data records of at most 512 bytes, where a count of zero means a full block.

AppleDosImage.cs writes DOS order: the VTOC at track 17 sector 0 (with $02 or $04 at offset 0 for 3.2 or 3.3, and a free-sector bitmap in which a set bit means free), a catalog chain on track 17 (three sectors on 3.2, sixteen on 3.3, seven 35-byte entries each), and a track/sector list of up to 122 pairs. DOS 3.2 allocates sectors in pairs, DOS 3.3 one at a time. The sector skew is an option and the identity by default, so the image is in logical DOS sector order.

Adding a format or a system

  1. Write a class implementing IExecutableFormat; return a failed OperationResult with a diagnostic rather than throwing or truncating.
  2. Register it in the ExecutablePublisher constructor, and add its name to the “Unknown output format” message and to the help text of CommandLineApplication.DisplayHelp.
  3. For a new system, add an Add(…) line to SystemCatalog.CreateSystems with its CPU, format, load address and symbol table; a machine with variants goes through HardwareOptions and HardwareProfile.
  4. Cover it with a test; the existing formats are pinned by golden-output tests in WinASM65.Tests.

GEOS applications on a D64

GEOS loads an application at the address written in its info block, or at an address the caller provides (LOAD2 reads it from $886C–$886D), and copies the bytes verbatim: the kernal does no relocation. WinASM65 therefore makes the application relocate itself. The geos verb links .w65 modules (or .w65a archives) and writes one application on a fresh D64 image:

WinASM65 geos main.w65 lib.w65 -o app.d64 -name "MY APP" -disk "WORK" -id 01 -author "Me"

The application record

The steps of RunGeos:

  1. Read the modules (expanding archives) and link them with Linker.
  2. GeosRelocationTable.Build(image, entry) lists every absolute reference of the linked image. A reference to the high byte of an address (lda #>Table) is refused with an exception that names the site (the verb does not catch it, so it ends the program): the high byte of a moved address depends on the carry out of the low byte, which the table does not carry. Low bytes are fine, because adding a bias modulo 256 commutes with taking the low byte. Relative branches, zero-page operands and immediates that are not addresses are not in the table.
  3. GeosStub.Assemble(origin, tableLength) assembles geos-stub.asm (an embedded resource) with WinASM65's own assembler, twice: once to measure it, once with the real distances, and checks that both passes have the same length. The stub contains no absolute address of its own: it reads the load address from $886C, reaches the table and the code by fixed offsets from it, uses only relative branches, and uses zero page $70–$7F.
  4. The record is loaded stub + table bytes below the origin, so the code lands exactly where it was linked; if that would go below $0000, the verb stops with an error.
  5. D64Builder writes the disk: one VLIR application with that single record, an info block, the directory entry and the BAM.

The table, at the head of the record after the stub:

$00-$03  "R65A"
$04-$05  the address the image was assembled for
$06-$07  number of entries
$08-$09  entry point of the program
$0A-     entries of 3 bytes: address low, address high, width

The info block's application area ($89–$9F) carries a summary: "R65A" at $89, the base address at $8D, the table address at $8F and the entry count after it. A kernal that ignores this area loads the file as usual.

The tests check the image field by field and check that applying the table gives the same bytes as linking at the new address; they do not run GEOS.

Text targets and the BASIC tokenizer

Applesoft under DOS or ProDOS, Waterloo Structured BASIC and BBC BASIC do not load a binary: they run an interpreter that reads a program of tokens, where each keyword is one byte. The basic verb writes that file from a plain-text program:

WinASM65 basic -f game.bas -o game.bin                      # the program as it sits in memory
WinASM65 basic -f game.bas -o game.po  -format prodos       # on a ProDOS volume
WinASM65 basic -f game.bas -o game.dsk -format dos33        # on a DOS 3.3 disk image
WinASM65 basic -f game.bas -o game.bin -dialect waterloo
WinASM65 basic -f game.bas -o game.bin -dialect bbc -list game.lst

Reading the source

BasicSource.Read cuts lines on carriage return and line feed only ($0B, $0C are legitimate inside strings), drops blank lines, and keeps the text after the line number verbatim. A program with no line numbers at all is numbered 10, 20, 30…; a program where only some lines are numbered is an error. A number that goes backwards is reported and the lines stay in file order, because the interpreter runs them in stored order.

Dialects

A BasicDialect is a token table plus a few rules (where the program starts, the highest line number, whether strings carry a length, how a line reference is written, how a line record is framed). One encoder and one decoder serve every dialect. BasicDialects.ByName maps the names a person types:

BBC BASIC stores a line number after GOTO, GOSUB, THEN, ELSE, RESTORE or ON as $8D and three bytes: the top two bits of each byte of the number are combined and exclusive-ORed with $54, and the remaining six bits of each byte are stored with bit 6 set, so no byte of a reference can be mistaken for a token. The Apple II version of Waterloo BASIC is not implemented: no source consulted describes its file layout.

The round trip

-list decodes the program that was just written with TokenDecoder, a reader written from the format rather than from the encoder, and renders it as text. The listing is byte-exact rather than pretty: a byte that is not a token comes back as \xNN, and anything that would read back as syntax is escaped, so the listing re-encodes to the same file:

10 PRINT \x05 \x48 \x45 \x4C \x4C \x4F
20 GOTO 1 0

The runtime stub for shared routines

A tokenised program has no fixed address, so a machine-code routine shared between two such programs cannot be linked into either. RuntimeBlock.Build(LinkedImage, RuntimeBlockOptions, diagnostics) packages a linked routine as a payload that carries no absolute address:

the stub        runtime-stub.asm, assembled at StubAddress (default $2000)
header, 10 B    destination, shift, entry offset, block length, site count
coded block     runs of three or more equal bytes coded as runs, the rest copied
site table      3 bytes per site: offset low, offset high, width

At run time the program does JSR to the stub, which expands the block at BlockAddress (default $4000), adds the shift to every listed site, calls the routine and returns. A one-byte absolute reference is refused, since a byte cannot hold an address that moved. Like the GEOS stub, it is assembled twice so that the header lands exactly after the code. This is a library API used by the tests (RuntimeStubTests runs the stub on the repository's own 6502 core, Execution/Cpu6502Core.cs); no command-line verb calls it yet.

TextFormat/AssemblyLexer.cs shares the namespace but not the subject: it is the token classifier the monitor's source editor uses to colour assembly source.
