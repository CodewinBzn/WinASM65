# Moniteur 6502 interactif — assemblage à la volée contre un émulateur

## Objectif

Un outil **externe** à l'assembleur : assemble, désassemble, lit et écrit
la mémoire de l'émulateur en direct, pose des points d'arrêt, et recharge
instantanément du code relocalisable à une nouvelle adresse — pendant que la
machine émulée tourne.

Le but n'est pas de concurrencer le débogueur de l'émulateur. C'est de faire
d'`AssemblerEngine` un outil **interactif**, et de valider le chargeur
relocalisable du socle `.w65` à vitesse humaine.

## Ce que le moniteur apporte que l'émulateur seul n'apporte pas

Le geste central, impossible aujourd'hui :

> « Charge cette routine partagée à `$C000`, puis à `$F000`, sans réassembler. »

Un assembleur classique produit un binaire figé à une adresse. Ici, la routine
est assemblée une fois, son graphe de relocations est conservé, et le
réassemblage à une autre adresse ne coûte qu'une application de deltas. C'est la
contrepartie interactive du linker (T4 du socle `.w65`), et la raison d'être du
projet.

## Décisions actées

1. **Option B : outil externe, liaison par socket.** WinASM65 ne dépend pas de
   l'émulateur ; l'émulateur ne dépend pas de WinASM65.
2. **Émulateur : Mesen**, via son API Lua.
3. **Réutilisable avec plusieurs émulateurs.** Le protocole est séparé de
   l'adaptateur ; chaque émulateur est un adaptateur, pas une refonte.
4. **Aucun linkage avec Mesen.** Mesen est GPL-3.0. Le pont est un script Lua
   propriétaire chargé par l'émulateur, qui ne dialogue avec l'assembleur que
   par socket. Aucun code n'est lié, donc aucune contamination de licence.
   C'est un avantage propre à l'option B, à préserver.

## Capacités de Mesen, vérifiées

Contrôlées le 2026-09-30 sur `mesen.ca/docs/apireference.html` et
`SourMesen/Mesen`, `SourMesen/Mesen2`.

| Besoin | API Mesen | Note |
|---|---|---|
| Lecture mémoire | `mem.read`, `mem.readWord` | **obligatoirement** via `memType.cpuDebug` |
| Écriture mémoire | `mem.write`, `mem.writeWord` | idem, variant Debug |
| Points d'arrêt mémoire | `emu.registerMemoryCallback` | la valeur retournée **remplace** la valeur lue/écrite |
| Exécution | `emu.break`, `emu.resume`, `emu.execute` | pas-à-pas disponible |
| État machine | `emu.getState`, `emu.setState` | |
| Sauvegardes | `emu.saveSavestate`, `emu.loadSavestate` | |
| Symboles | `debug.getLabelAddress` | |
| Liaison externe | LuaSocket `require("socket.core")` | **la passerelle** |
| Surcouche | `gui.drawString`, `gui.drawRectangle` | affichage in-emulator |
| Entrées | `emu.isKeyPressed` | |

### Pièges à écrire dans le code, pas seulement ici

- **Lecture avec effets de bord.** `memType.cpu` déclenche des effets
  d'émulation (registres drapeaux, PPU). Un moniteur qui lit en boucle pendant
  que la machine tourne altère l'état. **`memType.cpuDebug` exclusivement.**
- **`settimeout` obligatoire sur toute socket TCP.** Sans quoi le processus
  Mesen se fige. Documenté explicitement par Mesen.
- **L'API n'est pas stable.** Mesen le dit : « the API is not quite stable
  yet ». Le pont doit détecter la version et refuser de démarrer plutôt que
  d'échouer à mi-session.
- **Le dépôt `SourMesen/Mesen2` est archivé** depuis 2.1.1 (mi-2025) ; le
  projet vit maintenant dans `nesdev-org/MesenCE`. **Figer une version précise**
  dans le plan et dans le pont, sinon la maintenance devient impossible.
- **Autorisation I/O.** Certaines fonctions exigent l'option « Allow access to
  I/O and OS functions ». À vérifier et à documenter.

## Architecture

```
   WinASM65.Monitor (processus .NET)
     ├── cœur : ré-utilise WinASM65 (assembleur, liens, Linking/, Modules/)
     ├── session de liens en mémoire
     ├── désassembleur (table inverse)
     ├── boucle REPL
     └── client TCP ─────────────┐
                                 │  protocole texte, ligne par ligne
   Mesen.exe                     │
     └── script Lua (pont) ◄─────┘  mem.read/write via memType.cpuDebug
```

Le script Lua est **court et sans intelligence** : il traduit le protocole en
appels `mem.*`. Toute la logique reste du côté .NET, ce qui garde le pont
trivial à maintenir et le moniteur testable sans émulateur (contre un faux
`IMemoryBackend`).

## Protocole

Texte, ligne par ligne, sur `127.0.0.1`, port configurable. Suffisamment simple
pour être débogué au telnet. Les lectures en masse sont **bornées** (une requête
de 64 KiB renvoie 64 KiB, pas 64 millions de lignes).

| Commande | Effet |
|---|---|
| `PING` | disponibilité et version du pont |
| `READ <addr> <len>` | octets bruts |
| `WRITE <addr> <hex>` | écriture |
| `DISASM <addr> <count>` | texte désassemblé |
| `BREAK SET <type> <addr>` | point d'arrêt |
| `BREAK CLEAR` | tous supprimés |
| `PAUSE` / `RESUME` / `STEP` | contrôle d'exécution |
| `SYMBOLS <...>` | symboles du projet courant |
| `STATE SAVE` / `STATE LOAD` | instantanés |

Toute réponse porte un préfixe d'état : `OK …` ou `ERR <raison>`. Une écriture
partiellement refusée doit l'être explicitement, jamais silencieusement — même
principe que la validation de plage (P0).

## Le désassembleur

Point de départ technique, confirmé par lecture de `Cpu6502.cs`.

`NmosOpcodeTable` est un `Dictionary<string, byte[13]>` indexé par
`AddressingMode`, avec `0xFF` pour « non supporté ». L'inversion est directe :
parcourir la table, et pour chaque mode dont l'opcode n'est pas `0xFF`,
enregistrer `opcode → (mnémonique, mode)`. La longueur découle du mode :

| Modes | Longueur |
|---|---|
| `Implicit`, `Accumulator` | 1 |
| `Immediate`, `ZeroPage`, `ZeroPageX`, `ZeroPageY`, `IndirectX`, `IndirectY`, `Relative`, `ZeroPageIndirect` | 2 |
| `Absolute`, `AbsoluteX`, `AbsoluteY`, `Indirect`, `AbsoluteIndexedIndirect` | 3 |

Points d'attention :

- **Construire la table inverse par classe de CPU.** `Cpu65C02` surcharge
  `OpcodeTable`. Une table inverse partagée entre 6502 et 65C02 produirait des
  désassemblages faux sur les opcodes ajoutés.
- **Rendu de l'opérande**, l'exact symétrique de `ParseOperand`
  (`Cpu6502.cs:152-229`) : `#imm`, `abs`, `abs,x`, `abs,y`, `zp`, `zp,x`,
  `zp,y`, `(abs)`, `(zp,x)`, `(zp),y`. Les formes abrégées sont optionnelles.
- **Opcode inconnu : le signaler, ne jamais deviner.** Un `.byte` quelconque
  dans une ROM doit s'afficher comme tel, pas comme une instruction plausible.
- **Aller-retour exact.** Parce que l'assembleur applique
  `TryOptimizeZeroPage` (`Cpu6502.cs:252`), `lda $10` s'émet `A5 10`. Le
  désassembleur doit donc afficher la forme zéro-page, sans quoi
  désassembler puis réassembler ne serait pas idempotent.

## Séquencement — dépend du socle `.w65`

Ce plan **dépend de T4** (linker) du socle. Les répertoires `Linking/` et
`Modules/` existent déjà et sont en cours. Le moniteur ne doit pas les dupliquer.

| Tâche | Dépend de | Contenu |
|---|---|---|
| M0 | — | Décision de version Mesen, spike du pont Lua minimal |
| M1 | M0 | `IMemoryBackend` + faux backend testable sans émulateur |
| M2 | M0 | Script Lua du pont, `READ`/`WRITE`/`PAUSE`/`RESUME`/`PING` |
| M3 | M1, M2 | Table inverse du désassembleur + rendu des opérandes |
| M4 | M3 | `DISASM` dans le protocole, tests sur cas aller-retour |
| M5 | M1 | Points d'arrêt via `registerMemoryCallback` |
| M6 | T4 | **Rechargement relocalisable : le cœur de la valeur** |
| M7 | M4, M6 | REPL : assemblage, écriture en direct, affichage |
| M8 | M7 | `docs/monitor.md` |

**M0 d'abord, et c'est un vrai gate.** Le pont Lua est le seul élément dont
l'échec rend le reste inutile. Le prouver en premier, sur un vrai `.nes`, évite
de construire une architecture sur une hypothèse. Si Mesen ne convient pas, la
décision « option B + adaptateur » reste valable : seul l'adaptateur change.

M1 précède M2 volontairement : avec un `IMemoryBackend` et un faux backend, tout
le moniteur se teste sans lancer d'émulateur, ce qui rend les tâches suivantes
ordinaires.

## Validation

**Automatique, sans interface graphique.** Mesen expose un mode headless :

```
Mesen.exe --testrunner MyGame.nes Bridge.lua
```

et `emu.stop(code)` renvoie un code de sortie au processus. Un test d'intégration
est donc un script Lua qui lit, écrit, vérifie, et **sort avec un code non nul en
cas d'échec**. C'est ce qui rend la validation reproductible en CI, et c'est le
critère d'acceptation de M2 et de M6.

Pour le reste : golden octet-pour-octet sur le désassembleur, à comparer à la
sortie de l'assembleur — la même méthode que `DirectBurnGoldenTests.cs`, qui
dérive ses attentes des specs plutôt que de la sortie observée.

Non-régression : les 56 tests existants restent verts à chaque tâche.

## Risques

- **Instabilité de l'API Mesen.** Le risque n°1. Atténué par M0 et le
  verrouillage d'une version.
- **Effets de bord de lecture.** Une lecture avec `memType.cpu` corrompt
  l'état émulé. Atténué par une fonction d'accès unique, testée, qui **interdit
  physiquement** la variante non-Debug.
- **Mesen se fige sur une socket sans délai.** Symptôme grave : l'émulateur
  devient unresponsive et l'utilisateur croit qu'il a planté. Le pont met un
  `settimeout` sur toute connexion, sans exception.
- **Dérive du désassembleur.** Ajouter une instruction 65C02 sans mettre à jour
  la table inverse produit un désassemblage faux. Un test de cohérence
  « toute entrée de table a une sortie » est la garde.
- **Colonnes du protocole.** Sans bornes sur `READ`/`DISASM`, une requête
 d'exécution non bornée gèle l'émulateur. Bornes obligatoires, vérifiées par
  test.
- **Licence.** Le pont doit rester un script chargé, jamais lié. Revenir à un
  linkage ferait contaminer WinASM65 par la GPL.

## Hors périmètre

- Débogueur complet : registres, pile, breakpoints conditionnels. Mesen le fait
  déjà ; on ne le réécrit pas.
- Prise en charge d'un second émulateur. VICE, FCEUX etc. sont des **adaptateurs
  ultérieurs**, à prouver seulement après que le protocole a fait ses preuves
  sur un seul hôte.
- Graphique avancé. Le REPL suffit ; la surcouche `gui.*` est un supplément
  ultérieur.

## Question ouverte

**Version de Mesen à figer.** À trancher avant M0 : `MesenCE` (actuel) ou
`Mesen2` 2.1.1 (archivé mais documenté). Cela conditionne les signatures de
l'API Lua et donc l'adaptateur.
